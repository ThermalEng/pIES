# 财务计算

> 文档状态：生效蓝图；代码边界：`backend/iesplan/finance/`

## 作用

`finance` 把建设投入、运行结果和经济假设转换成可解释的现金流与财务指标。它必须让每个指标的口径、时间点和状态可复核，避免把一个看似正常的数字当作完整财务结论。

## 边界

模块负责：

- 财务参数的领域结构与校验；
- 项目和资本金现金流；
- NPV、IRR、LCOE、回收期等指标及状态分类；
- 从规范运行汇总生成不可变 `FinancialResult`。

模块不负责从数据库找价格、不选择当前项目版本、不判断用户权限、不调度任务，也不修改计算结果。设备技术文件不提供任何价格或成本；规划阶段已经使用的设备投资、运维成本和能源购售价格必须作为明确、可追溯的经济输入随运行汇总传入，finance 不从设备定义重新推断。

规划经济与财务评价是两个连续但不同的边界：规划经济输入影响“建什么、建多大、怎样运行”，必须在求解前进入配置；finance 在方案确定后解释建设计划和运行结果，形成税、折旧、融资、现金流及评价指标。不得把全部价格留到求解后，否则容量和运行决策无法反映经济性。

## 输入

| 输入 | 关键要求 |
|---|---|
| 建设与替换计划 | 金额币种、发生期和是否含税明确 |
| 逐时或年度运行汇总 | 能量、成本、收益的单位和时间范围明确 |
| `FinanceParams` | 评价周期、折现率、税率、折旧、融资和基准口径完整 |
| 财务基准 | 与当前方案使用同一时间、价格和核算边界 |

金额与需要精确往返的费率使用十进制定点语义；物理量来自规范计算输出。模块不能自行读取“最新价格”补齐缺失输入。

## 输出

`FinancialResult` 至少表达：

- 逐期项目和资本金现金流；
- 投资、运行成本、收益和残值等组成；
- NPV、IRR、LCOE、回收期及单位；
- 每个无法正常计算指标的独立状态与原因；
- 财务参数摘要、币种、评价期和计算版本。

IRR 必须与 `normal、no_solution、multiple、degenerate、out_of_domain、numeric_failure` 等状态一起消费；不能用 `null` 或零模糊这些情况。

## 开发思路

1. 先把输入规范成时间点明确的现金流分量；
2. 再组合项目现金流和资本金现金流；
3. 对每个指标独立计算并分类失败状态；
4. 做内部一致性检查，例如分量之和、时间长度和币种一致；
5. 最后形成不可变财务结果，交给 analysis 和证据层。

财务指标函数应保持纯计算。application 负责选择哪份快照和基准，finance 只解释已明确传入的事实。

## 增加财务指标

1. 写清业务定义、单位、时间点和适用范围；
2. 明确输入不足、分母为零、多解或无解时的状态；
3. 用手算小样例和边界现金流建立测试；
4. 将指标加入 `FinancialResult` 的版本化 contract；
5. 更新 analysis 对指标的读取，但不让 finance 依赖 analysis；
6. 同步结果解释和更新日志中的用户可见变化。

## 失败语义

- 币种或评价期不一致：拒绝计算；
- 非有限值、长度错误或缺少必需分量：输入诊断；
- IRR 无解、多解或退化：返回对应业务状态，不抛普通内部异常；
- 数值算法未收敛：返回 numeric failure 和受控细节；
- 基准缺失：由 application 在调用前阻断，finance 不创建零基准。

## 必须遵循的规范

- 金额口径、币种和时间点必须显式；
- 百分比进入模块前已是规范比例；
- 不依赖 computation 内部实现、HTTP、ORM 和全局价格表；
- 不用浮点显示舍入值反推现金流；
- 每个指标的状态不能被综合分数覆盖；
- 财务输入和模块版本写入快照或证据。

## 完成标准

- 手算基准、正常现金流及 IRR 各异常状态均有测试；
- 项目和资本金口径不会混用；
- 输入不完整时没有默认现金流或伪指标；
- 结果可序列化、可追溯且足以生成用户解释；
- 新指标不要求 finance 读取项目或任务内部状态。

代码阅读从公开 `FinanceParams`、`FinancialResult` 和指标入口开始，再阅读现金流构造与数值算法；对应测试以财务模块测试为入口。
