# 设备目录

> 文档状态：生效蓝图；代码边界：`backend/iesplan/devices/`

## 作用

`devices` 回答“系统认识哪些设备，以及每类设备具有哪些纯技术语义”。它发布的是统一设备说明，不是设备在某个项目中的实例，也不执行计算。

设备描述是 GUI、建模、装配和配置校验共同依赖的事实源。公开文件形态固定为 [设备模型 YAML](../formats/device-model-yaml.md)。增加设备时，应扩展 descriptor/provider，而不是在前端、装配或生成器中分别增加同名判断。

## 边界

模块拥有：

- 稳定设备类型 ID、名称键和分类；
- 不随时间变化的技术 properties、规范单位和值域；
- 序列 interfaces、carrier、五类接口语义和值域；
- properties、接口序列与内部变量之间的声明式 equations；
- 设备 provider 的发现、校验和原子发布。

模块不拥有项目设备 ID、画布坐标、连接实例、存量/新增身份、规划变量、计算精度、算法选择、经济配置和运行结果。设备价格、成本、税务、折旧和财务假设不得由 descriptor 引用；调用方不能读取目录路径。

## 输入

| 来源 | 输入 | 进入条件 |
|---|---|---|
| 内置或外部 provider | 一组 `ies.device-model` YAML 或等价候选描述 | provider ID、版本和依赖明确，设备内容有规范摘要 |
| 单位规范 | property 与 interface 单位 ID | 单位存在且量纲正确 |
| 方程契约 | relations、内部变量和时间索引 | 标识符、单位和值域可完整校验 |
| 序列数据 | `predefined` interface 所引用的数据版本 | step、单位、分辨率和适用范围明确 |

无论 provider 如何发现文件，进入目录前都必须符合相同设备模型 schema；目录路径、远端服务和包入口只是实现选择，不属于其他模块可依赖的输入方式。时序样例使用[设备数据 CSV](../formats/device-data-csv.md)。

用户“模型库”的结构化表单、在线 YAML 编辑和 YAML 上传都必须调用本模块同一个安全解析、校验、规范化和 descriptor 入口。用户目录和共享审批不属于 devices；但模型能否发布、是否可用于装配的语义结论必须由 devices 公开门面给出，不能由 application 或前端复制校验。

项目内新建模型同样先调用本模块校验候选字节。`devices` 返回规范候选、内容摘要、校验回执或完整诊断，不负责分配项目 `_N` 编号和写项目目录；这些原子保存动作由 application 编排。非法候选不得进入已发布目录快照或可选择目录。

## 输出

主要输出是不可变 `DeviceDescriptor` 集合。每个描述至少保证：

- 类型 ID 稳定，规范内容摘要唯一；
- property、interface、内部变量和 relation ID 在该内容内唯一；
- 所有常量、单位、有效区间和接口类型可以解释；
- 技术方程和预定义数据需求结构完整；
- 不含目录路径、解析器对象或前端组件信息。

候选校验失败时输出有稳定顺序的 `Diagnostic` 集合，至少可表达字段路径、消息键、expected/actual，并在解析器可知时携带 YAML 行列。校验器应聚合同一阶段互不依赖的问题；结构已经不足以安全解释后续字段时才停止后续阶段。

消费者按用途读取同一描述：GUI 生成通用 property 表单和接口，modeling 校验并转换方程，assembly 校验项目实例与序列连接，application 校验用户提交。

## 初始化与发布流程

```text
发现 provider
    ↓
读取候选设备描述
    ↓
逐项校验 ID / 内容摘要 / properties / interfaces / 单位 / equations / 数据引用
    ↓
校验集合内重复与依赖
    ↓
一次性发布新目录快照
```

候选集合验证完成前不能替换现有状态。正式发布前不支持运行期热加载；实例启动后的目录在本次进程生命周期内保持稳定。

## 增加一种设备

1. 按设备模型 YAML 写出可独立校验的设备说明，选择稳定、带命名空间的设备类型 ID；
2. 定义不随时间变化的纯技术 properties、单位和值域，不写价格或成本；
3. 定义每个序列 interface 的 carrier、单位、值域和 `in/out/bidirectional/predefined/blind` 类型；缺省只允许成为 `blind`；
4. 为 `predefined` 选择 `constant/data_repeat/data_predict`，为内部序列变量和跨步关系写出 equations；
5. 校验受限方程，不写函数/包/模块路径、任意代码或计算精度；
6. 提供合法/非法 YAML、最小/典型数据 CSV 和 provider 契约测试；
7. 用目录 API、GUI schema、装配校验验证同一描述贯通，而不是修改消费者的设备类型表。

## 失败语义

| 情况 | 处理 |
|---|---|
| 设备 ID 或内容身份冲突 | provider 注册失败，不发布候选集合 |
| 单位、值域或接口类型非法 | 给出精确配置诊断，实例不 ready |
| 方程引用、单位或时间关系非法 | 技术模型校验失败，不发布 descriptor |
| 字段类型、interface type 或 source 组合非法 | 返回完整候选诊断，不保存项目模型 |
| 配套周期/预测文件非法或缺失 | 返回数据诊断，模型与临时文件均不正式落盘 |
| 请求未知设备类型 | 明确“未注册”错误，不返回默认设备 |
| provider 读取失败 | 保留失败原因，不回退静态内置表 |

## 必须遵循的规范

- 外部模块只调用设备公开门面；
- descriptor 不携带项目状态或可变运行对象；
- 设备文件遵守 `ies.device-model`，未知核心字段和可执行入口拒绝；
- 名称和说明使用消息键，领域 ID 不随语言变化；
- property 值是设备技术契约的一部分，必须有单位和适用条件；
- 设备文件不使用独立语义版本；改变任何技术语义都会改变规范内容摘要；
- 历史任务必须能够读取其固定的设备内容摘要和 schema 校验回执。
- 候选校验是正式保存的前置门禁，不能先写项目目录再异步判定是否合法。

## 完成标准

- provider 的成功、重复、缺依赖和半失败均有协议测试；
- 新设备无需修改前端接口规则、assembly 类型表或全局注册表；
- 目录快照确定、排序稳定、可序列化且保留设备模型摘要；
- GUI、建模和装配消费的是同一公开描述；
- 未交付的设备能力不得出现在正式使用者指南。

代码阅读从 `devices` 公开门面和 descriptor 类型开始，再进入 provider、加载与模块私有注册实现；对应测试以设备目录和初始化测试为入口。
