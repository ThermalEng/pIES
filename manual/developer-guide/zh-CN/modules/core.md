# Core 基础能力

> 文档状态：生效蓝图；代码边界：`backend/iesplan/core/`

## 作用

`core` 为所有模块提供一套无业务状态的共同语言：怎样表达诊断、时间轴、单位、标识符、规范 JSON 和基础错误。它的价值不是“方便放公共代码”，而是让业务模块在不相互依赖的情况下交换含义一致的值。

开发 `core` 时要问：这个能力是否在不知道项目、设备、任务或用户的情况下仍然成立？只有答案为“是”时才属于这里。

## 边界

`core` 负责：

- 不可变的基础 contract 和值对象；
- 诊断与应用错误的基础结构；
- 单位和量纲规则、时间轴、稳定 ID、摘要与规范序列化；
- 密码哈希、随机令牌等不含业务策略的安全原语。

`core` 不负责：

- 设备、方程、generator、solver 或其他 provider/内容注册；
- 项目默认值、任务状态、权限决策或业务校验；
- 数据库、缓存、对象存储和网络访问；
- 为某个上层模块提供带业务名称的便捷包装。

## 输入与输出

| 输入 | 进入条件 | 输出 | 保证 |
|---|---|---|---|
| 数值与单位 ID | 单位已声明、数值有限 | 规范值或单位诊断 | 量纲一致，不猜单位 |
| 时间起点、分辨率、点数 | 时区和分辨率明确 | 不可变时间轴 | 长度、顺序和时间语义确定 |
| 诊断码、参数和位置 | 诊断码已登记 | `Diagnostic` | 可序列化、可定位、无本地化正文 |
| 任意可规范化数据 | 类型属于允许集合 | 规范 JSON/摘要 | 相同语义产生相同字节和哈希 |
| 原始秘密 | 由可信调用方提供 | 哈希或随机令牌 | 不回传明文，不写日志 |

上层模块只能依赖公开输出，不能依赖 `core` 内部缓存、字典或解析过程。

## 开发思路

一项基础能力通常按四层组织：

1. **值对象或枚举**定义允许表达的状态；
2. **纯校验函数**拒绝非法值并给出结构化原因；
3. **纯转换函数**完成唯一、可逆或明确有损的规范化；
4. **公开门面**只导出长期需要的最小集合。

函数应在相同输入下产生相同输出。若需要读取环境变量、数据库或 provider，应由组合根或业务模块读取后把明确参数传入，而不是让 `core` 自行发现环境。

## 诊断与失败

- 调用方输入不合法：返回诊断或抛出明确 `AppError` 子类；
- 单位不兼容：拒绝转换，不返回原值；
- 时间轴不完整：列出可定位问题，不补点或排序掩盖错误；
- 未登记诊断码：开发期立即失败，不能生成临时代码；
- 无法规范序列化：拒绝计算摘要，不使用对象字符串表示兜底。

选择“返回诊断”还是“抛异常”取决于调用方式：面向用户的一批输入校验应尽量聚合诊断；违反编程契约或无法继续的内部调用应显式失败。

## 增加基础能力

1. 证明它不拥有业务事实，也不需要业务依赖；
2. 定义输入域、输出域、空值和失败语义；
3. 明确单位、精度、时区、排序或编码规则；
4. 先写边界值和性质测试，再实现纯函数；
5. 只从公开门面导出稳定能力；
6. 至少让两个合理的上层场景复用，避免为单一调用点制造“公共”包装。

## 必须遵循的规范

- `core` 的依赖图只能指向标准库或明确批准的基础库；
- 不以 `dict[str, Any]` 替代已经稳定的值对象；
- 不接受 `NaN`、无穷值、含糊时区或未声明单位；
- 诊断只保存消息键和结构化参数，不保存用户文案；
- 标识符和摘要不能与普通显示字符串混用；
- 性能缓存如有必要，必须可丢弃且不改变结果。

## 完成标准

- 纯函数测试覆盖正常值、边界值、非法值和确定性；
- `core` 不导入任何业务模块；
- 输出可以稳定序列化并跨进程使用；
- 错误不会被默认值、空数组或宽泛异常隐藏；
- 新公开符号有清晰语义，并已在需要它的模块协议测试中使用。

代码阅读从公开门面开始，再阅读对应的诊断、单位或时间实现；测试入口位于 `backend/tests/` 中名称相同的基础能力测试。
