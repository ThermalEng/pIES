# 领域模型与追溯链

> 文档状态：生效蓝图；规范版本：1.0.0；上位规范：[架构宪法](ARCHITECTURE_CONSTITUTION.md)

## 权威事实

pIES 把信息按生命周期分为三类：

| 类型 | 示例 | 规则 |
|---|---|---|
| 可编辑工作状态 | 项目草稿、未提交表单 | 可变更，但每次持久化形成明确修订 |
| 不可变业务证据 | 项目版本、数据版本、计算快照、结果、评估 | 只能追加，不原地覆盖 |
| 可重建运行状态 | 队列、进度、心跳、缓存 | 丢失后可从权威事实恢复 |

数据库保存项目、权限、任务和证据索引等事务事实；缓存系统不能成为唯一来源。大型不可变内容通过统一对象协议保存，业务模块只持有对象标识与引用。

## 项目聚合

项目定义币种、不可变计算基线、生命周期和访问成员。项目草稿包含：

- 设备、真实序列 interfaces 和连接组成的系统图；
- 已确认的数据集版本绑定；
- 规划配置、公共财务配置和计算配置及其修订；
- 用户尚未提交计算的编辑状态。

项目创建时同时固定不可变计算基线：全项目时间分辨率、是否考虑闰年和场景模式。当前场景模式只支持 `single`，序列使用连续 `step` 而非时间戳/时区。项目基线创建后不修改；多场景与基线变更放入 `1.0.0` 之后的 Roadmap。

项目版本是草稿在某个业务时点的不可变固化。自动保存只更新草稿修订，不能冒充项目版本。

项目模型目录只保存已经通过后端完整校验的规范模型文件。编辑中的候选 YAML 和临时数据文件不是项目模型事实；校验失败不创建目录条目、不参与装配，也不占用正式 `_N` 编号。校验成功后，模型文件、配套数据、内容摘要、校验回执和目录引用作为一个应用用例原子提交。

## 数据集

数据集是名称和溯源容器；每次上传产生新的不可变数据集版本。原始版本必须绑定 step 规则、采样间隔、字段、单位、质量结果、来源和内容摘要。进入装配的计算序列版本必须已按项目基线完成重采样、周期展开或默认预测训练/生成，并固定基线摘要、连续 step、点数、变换/训练回执和输出摘要。

项目必须明确绑定一个通过质量门禁的数据版本。上传新版本不能静默改变历史任务或现有绑定。

## 规划、财务与计算配置

规划配置只描述目标函数/权重、规划变量、容量上下界和规划/系统约束。它不保存财务参数或 generator/solver 选项。

财务配置是整体系统模型的公共财务参数输入，只保存规划与结果财务计算共同使用的设备单价、投资、固定/可变 O&M、能源购售价格、税率和资金时间成本等参数。它不保存目标函数、规划变量/约束、计算选项或仅在某一阶段使用的数据。规划生成与结果财务计算必须引用同一不可变财务配置 revision。

计算配置只描述把规范装配产物转换为计算包的方法：mode、generator、solver、计算精度、离散化、容差、时间限制、选项、随机种子和输出选择。计算配置不进入 assembly 内容摘要，在计算包生成时与 `ValidatedAssemblyArtifact` 一起固定。三类配置保存均形成修订，历史任务按当时明确 revision 解释。

存量设备的历史投资按沉没成本处理，不重复进入新增投资；新增设备投资必须与候选容量变量绑定。目标函数只定义在规划配置中，可引用公共财务配置的参数；财务配置本身不表达优化意图。

表单显示值不等于契约值。例如百分数可在 GUI 中显示为 `8%`，公开契约使用规范比例；转换属于前端 mapper，后端仍负责范围和领域约束。

## 用户自定义内容

用户自定义内容由“可编辑条目”和“不可变发布内容”组成。条目保存名称、类型、所有者和当前生命周期；草稿每次保存形成 revision。设备模型发布时固化 revision、`schema_version`、内容摘要、来源和校验回执，不在设备文件内声明独立语义版本；算法插件仍发布精确语义版本和依赖锁。项目和计算配置只能引用已安装、校验通过且当前可用的设备内容摘要或插件精确版本，不能引用草稿、上传文件名或“最新内容”。

模型库的三种作者入口——网页结构化表单、在线 YAML 编辑和 YAML 上传——都必须产生同一 `ies.device-model` 规范对象。算法插件以 `ies.algorithm-plugin` ZIP 保存，其中加工程序把规范装配转成求解文件，算法程序执行求解，结果声明支持统一适配。插件由独立隔离运行器执行，不进入普通进程模块空间。

“共享”与“安装”是两个独立事实：所有者提交设备不可变内容 revision 或插件精确版本的共享申请，管理员批准后该内容进入共享园地；其他用户安装时只增加指向同一不可变内容的引用，不复制底层对象。停止共享阻止新的安装，但不能破坏既有安装、项目版本、快照或证据；用户从目录卸载也只解除自己的目录引用，仍被历史对象引用的内容不能物理清理。

## 快照、任务和结果

```text
项目版本 + 数据版本 + 规划/财务配置版本 + 设备内容摘要
                         ↓
               ValidatedAssemblyArtifact
                         ↓
            + 计算配置/provider 版本
                         ↓
                    CalcSnapshot
                         ↓
                 Task → Attempt
                          ↓
      ValidatedAssembly → Solver Bundle → ExecutionReceipt → Result
                         ↓
                 Evidence / Assessment / Export
```

计算快照固定规范装配摘要与校验回执、输入资源摘要、schema 版本、设备规范内容摘要、规划/财务/计算配置 revision、generator/solver/executor/result adapter 版本、单位契约、随机种子、选项和容差。任务执行期间不得重新读取不断变化的项目草稿。

任务的技术状态与业务结局正交：任务可以正常完成，但业务上没有推荐方案或证据不足。重试创建新的执行尝试，但沿用相同逻辑输入。

结果、评估和导出必须能追溯到任务、有效执行尝试、快照、对象摘要和依赖版本。历史结果只能按当时快照解释，不能用当前项目或最新数据替代。

## 对象生命周期

对象存储以内容摘要识别不可变字节。引用清单由明确的所有者、所有者标识和用途组成，是对象是否可清理的权威事实。

- 创建或替换业务资源时成对附加/解除引用；
- 任一有效引用都阻止清理；
- 引用计数如存在，只能是可重建缓存；
- 文件与元数据之间的失败使用幂等恢复与 reconciliation 处理；
- 导出不能留下脱离管理的静默副本；
- 对象清理执行软删/保留期（待物理回收标记），保留期内可恢复，到期才物理删除，避免管理员误操作不可恢复。

## 身份、权限和审计

后端是认证与授权的唯一权威。项目所有者与管理员能力必须显式区分，重点用于避免普通使用者越权和管理员误操作；前端隐藏按钮只改善体验，不能代替后端检查。默认部署模型下，管理员是受信任运维角色，不要求管理员相互隔离或双人审批。

权限变化、对象清理、项目/数据/计算配置、恢复和评估等关键变更应留下不可变、最小化的脱敏审计记录；普通查看和日常运维不要求重型审计。不得记录密码、令牌、内部路径或不受控大对象。

## 开发时怎样选择对象形态

遇到一个新业务数据时，按以下顺序判断：

1. 用户是否需要继续编辑？需要则先设计草稿和 revision；
2. 它是否被任务、结果或审批引用？被引用的形态必须形成不可变版本；
3. 内容是否较大？大内容交给 storage，领域只保存 handle 和摘要；
4. 丢失后能否从数据库事实重建？可以则属于运行状态或缓存；
5. 是否需要解释历史？需要则保存来源、schema 和依赖版本，而不仅是最终数字。

不要因为数据库表已有 `updated_at` 就把记录视为版本，也不要因为对象带哈希就自动获得业务语义。版本的形成必须对应明确业务动作。

## 典型生命周期

### 数据集上传

```text
创建/选择数据集容器
  ↓ 上传字节到 storage
形成不可变数据版本 + 质量报告 + owner 引用
  ↓ 用户确认
项目草稿绑定明确数据版本
  ↓ 提交任务
CalcSnapshot 固定该绑定与对象摘要
```

上传新文件只增加数据版本，不能改变旧绑定和历史任务。

### 项目计算

```text
项目草稿 revision
  ↓ 固化业务版本
项目版本 + 数据版本 + 配置版本
  ↓ assembly
ValidatedAssemblyArtifact → CalcSnapshot
  ↓ Worker attempt / generator
Solver Bundle
  ↓ runtime / result adapter
ExecutionReceipt → Evidence / Result / Assessment / Export
```

每个箭头都应能通过公开 ID 和摘要反向追溯。候选方案应用属于新的项目版本动作，不允许原地修改来源版本。

## 增加一个版本化资源

1. 定义草稿、版本和删除/保留状态是否都需要；
2. 明确哪个用户动作创建版本；
3. 选择规范序列化和摘要算法；
4. 保存创建者、时间、schema、来源版本和外部依赖；
5. 让数据库约束禁止已发布内容被更新；
6. 定义对象引用的 attach/detach 时点；
7. 测试并发创建、重复提交、历史读取、导出和恢复。

## 完成标准

- 草稿、版本、快照、证据和缓存没有混用；
- 历史资源不依赖当前项目或最新 provider 才能解释；
- 删除、归档、保留和对象清理的关系明确；
- 所有不可变对象都能定位创建动作、来源与版本；
- 前端显示的“版本”能对应一个真实、可查询的领域对象。
