# 领域模型与追溯链

> 文档状态：生效蓝图；规范版本：1.0.0；上位规范：[架构宪法](ARCHITECTURE_CONSTITUTION.md)

## 权威事实

pIES 把信息按生命周期分为三类：

| 类型 | 示例 | 规则 |
|---|---|---|
| 可编辑工作状态 | 项目草稿、未提交表单 | 可变更，但每次持久化形成明确修订 |
| 不可变业务证据 | 项目版本、数据版本、计算快照、结果、评估 | 只能追加，不原地覆盖 |
| 可重建运行状态 | 队列、进度、心跳、缓存 | 丢失后可从权威事实恢复 |

数据库保存项目、权限、任务和证据索引等事务事实；缓存系统不能成为唯一来源。大型不可变内容通过统一对象协议保存，业务模块只持有对象标识与引用。

## 项目聚合

项目定义所有者、币种、不可变计算基线和生命周期。项目草稿包含：

- 设备、真实序列 interfaces 和连接组成的系统图；
- 已确认的数据集版本绑定；
- 规划配置、财务文件契约和计算配置及其修订；
- 用户尚未提交计算的编辑状态。

项目创建时同时固定不可变计算基线：全项目时间分辨率、场景模式与运行起始年（无闰年字段，闰年逐年按公历推导）。当前定义的场景模式为 `single`，序列使用连续 `step` 而非时间戳/时区。项目基线创建后不修改；多场景或允许变更基线必须通过新的公开契约定义。

项目版本是草稿在某个业务时点的不可变固化。自动保存只更新草稿修订，不能冒充项目版本。

每个项目的可编辑工作区即其草稿。切换计算任务时，将该任务的整套冻结输入载入草稿；后续编辑只改变草稿，不修改历史任务。只有用户发起计算时，才将当时草稿中的输入固化为具有独立 ID 的新任务；切换任务、编辑和自动保存均不创建计算任务。

项目包导入形成独立的新项目，由导入者拥有，原项目与账号授权不随之改变。包内历史版本必须携带恢复所需的精确配置与数据依赖；导入时将这些依赖及引用映射到新项目，保持各版本的实际业务值与缺席状态，不能用当前配置替代历史配置，也不能继续引用原项目的内部身份。历史结果作为证据来源保留，不伪造本地计算任务。

导入提案与正式项目是不同的业务状态。确认前只保存提案、已接受内容与其暂存引用，不创建或发布普通项目；关闭确认界面不表示已导入成功。确认时，新项目身份、所有权、草稿、版本、配置、对象引用与提案应用状态在同一数据库事务中发布；失败不留下半成品项目，已接受提案仍可重试。提案持有期间所需对象按存储引用生命周期保留，不以前端隐藏、空草稿或跳过错误代替完整发布。

项目模型目录只保存已经通过后端完整校验的规范模型文件。编辑中的候选 YAML 不是项目模型事实；校验失败不创建目录条目、不参与装配，也不占用正式 `_N` 编号。校验成功后，模型文件、校验回执和目录引用作为一个应用用例原子提交。项目模型保存不接受、不校验、不落盘也不关联 `data_files`；数据文件由数据集流程独立管理，并由项目装配实例的 `predefined_interfaces` 显式绑定。

## 数据集

数据集是名称和溯源容器；每次上传产生新的不可变数据集版本。原始版本必须记录 step 规则、采样间隔、字段、单位、质量结果、来源和对象标识，但数据文件本身不能成为项目来源绑定权威。进入装配的数据必须已完成严格校验和表示规范化；装配实例以 `predefined_interfaces` 的严格判别联合固定 `constant/data_repeat/data_full/data_predict` 来源声明和不可变数据引用。原始来源与项目基线分辨率一致并各自保持连续 `step`；`data_repeat` 的完整来源序列可为完整日、周或年，整体作为重复基线，`data_full` 必须原样覆盖全周期全部点数。全周期计算序列在计算阶段物化后才统一点数和 `step`，并固定项目基线引用、预测/展开回执和输出引用；可信内部流程按既有引用交接。

项目必须明确绑定一个通过质量门禁的数据版本。上传新版本不能静默改变历史任务或现有绑定。

## 规划、财务与计算配置

规划配置只描述目标函数/权重、规划变量、容量上下界和规划/系统约束。它不保存财务参数或 generator/solver 选项。

财务方法由不可变财务模型定义，项目财务配置选择其精确修订并提供参数和输入绑定。地区 `FinanceProfile` 提供成本与价格基准；项目 `FinanceOverrides` 提供覆盖、模型选择与项目参数；合并器将两者与所选模型正文形成唯一的不可变 `EffectiveFinanceConfig`。规划生成与结果评价消费同一冻结规则，不各自维护业务公式。字段以[财务 YAML](formats/finance-yaml.md)与[财务模型 YAML](formats/financial-model-yaml.md)为准；目标选择仍归规划配置，计算选项仍归计算配置。

建设与运营时间、折现率、付款和维护安排属于任务的显式评价确认，随任务冻结，不回流财务三件套。生成阶段通过同次物化输入携带这份确认，不另增核心输入或读取当前草稿；归属与时轴见[财务计算](modules/finance.md#评价确认与快照冻结)。

计算配置只描述把规范装配产物转换为计算包的方法：mode、预测目标所用算法与参数、generator、solver、计算精度、阶段二适用时的收敛容差与最大迭代数、时间限制、选项、随机种子和输出选择。计算配置不进入 assembly，在计算包生成时与 `ValidatedAssemblyArtifact` 一起固定。三类配置保存均形成修订，历史任务按当时明确 revision 解释。

存量设备的历史投资按沉没成本处理，不重复进入新增投资；新增设备投资必须与候选容量变量绑定。目标函数只定义在规划配置中，可引用 `EffectiveFinanceConfig` 的参数；财务参数本身不表达优化意图。

表单显示值不等于契约值。例如百分数可在 GUI 中显示为 `8%`，公开契约使用规范比例；转换属于前端 mapper，后端仍负责范围和领域约束。

## 用户自定义内容

用户自定义内容由“可编辑条目”和“不可变发布内容”组成。条目保存名称、类型、所有者和当前生命周期；草稿每次保存形成 revision。设备模型发布时固化 revision、`schema_version`、来源和校验回执，不在设备文件内声明独立语义版本；算法插件仍发布精确语义版本和依赖锁。项目和计算配置只能引用已安装、校验通过且当前可用的设备 revision 或插件精确版本，不能引用草稿、上传文件名或“最新内容”。

模型库的三种作者入口——网页结构化表单、在线 YAML 编辑和 YAML 上传——都必须产生同一 `ies.device-model` 规范对象。算法插件以 `ies.algorithm-plugin` ZIP 保存，其中加工程序把规范装配转成求解文件，算法程序执行求解，结果声明支持统一适配。插件由独立隔离运行器执行，不进入普通进程模块空间。

“共享”与“安装”是两个独立事实：所有者提交设备不可变内容 revision 或插件精确版本的共享申请，管理员批准后该内容进入共享园地；其他用户安装时只增加指向同一不可变内容的引用，不复制底层对象。停止共享阻止新的安装，但不能破坏既有安装、项目版本、快照或证据；用户从目录卸载也只解除自己的目录引用，仍被历史对象引用的内容不能物理清理。

## 快照、任务和结果

```text
项目版本 + 数据版本 + 规划/财务配置版本 + 设备 revision
                         ↓
               ValidatedAssemblyArtifact
                         ↓
            + 计算配置/provider 版本
                         ↓
                    CalcSnapshot
                         ↓
                 Task → Attempt
                          ↓
      序列物化 → 阶段一完整求解
                          ↓
           [多预测时]阶段二迭代求解
                          ↓
      ValidatedAssembly → Solver Bundle/ExecutionReceipt → Result
                         ↓
                 Evidence / Assessment / Export
```

计算快照固定规范装配与回执、输入资源、逐装配实例设备数学贡献、规划/财务/计算配置及其精确修订、评价确认和 provider 依赖。财务模型正文、项目参数与绑定随有效财务配置固定；确认字段与快照版本见[公共契约](contracts.md#快照与异步契约)。任务执行期间不得重新读取当前草稿、设备目录或最新财务模型替代冻结内容。

任务的技术状态与业务结局正交：任务可以正常完成，但业务上没有推荐方案或证据不足。重试创建新的执行尝试，但沿用相同逻辑输入。

结果、评估和导出必须能追溯到任务、有效执行尝试、快照、对象引用和依赖版本。历史结果只能按当时快照解释，不能用当前项目或最新数据替代。

财务结果是模型声明的现金流及其指标的同源封存事实，具有独立于输入快照的契约版本；口径、单位和指标来源按同任务冻结声明解释，不以输出名称猜测，也不在读取或导出时重算。结果形态见[财务计算](modules/finance.md#封存评价块-financial_evaluation)。

结果、评估和报告导出跟随同一所选任务；无明确选择时默认最新完成的计算任务。所选任务尚未完成或没有可用结果时，不显示计算结果、不允许报告导出，也不回退到其他任务。报告导出前须完成该任务结果的评估。

选择结果与应用方案是不同操作：选择记录用户采用的结果，应用则把该结果的真实规划参数写入新的项目工作状态并创建新版本，不能仅保存一个无业务消费者的采用标记。参数来源为不可变计算结果，目标关系来自同一计算快照中的规划变量与设备实例参数绑定；不得按设备类型、显示名称或指标键猜测目标，也不得把仅有指标而没有参数解的结果伪装成可应用方案。历史结果页的输入来源说明同样使用原任务快照，不能展示当前项目数据版本冒充历史来源。

应用方案以任务快照引用的计算来源版本为基线：在该版本的工作状态上写入所选解的规划参数，派生新版本并将其设为当前工作状态，不叠加当前草稿，也不带入计算后新增的编辑。新版本保留来源版本与结果的追溯关系；来源版本、既有草稿修订、结果和证据保持不可变。执行前必须向用户明确展示来源版本、参数变更及当前工作状态将被替换的影响，并取得确认；参数写入、新版本创建与当前状态切换须在同一应用事务中完成，失败不发布部分状态。

## 对象生命周期

对象存储以对象 ID 识别不可变字节。引用清单由明确的所有者、所有者标识和用途组成，是对象是否可清理的权威事实。

- 创建或替换业务资源时成对附加/解除引用；
- 任一有效引用都阻止清理；
- 引用计数如存在，只能是可重建缓存；
- 已明确发生的文件写入中断使用操作 ID 幂等重试，不扫描或复核其他对象；
- 导出不能留下脱离管理的静默副本；
- 对象清理执行软删/保留期（待物理回收标记），保留期内可恢复，到期才物理删除，避免管理员误操作不可恢复。

## 身份、权限和审计

后端是认证与授权的唯一权威。项目所有者与管理员能力必须显式区分，重点用于避免普通使用者越权和管理员误操作；前端隐藏按钮只改善体验，不能代替后端检查。默认部署模型下，管理员是受信任运维角色，不要求管理员相互隔离或双人审批。

权限变化、对象清理、项目/数据/计算配置、恢复和评估等关键变更应留下不可变、最小化的脱敏审计记录；普通查看和日常运维不要求重型审计。不得记录密码、令牌、内部路径或不受控大对象。

管理员通过只读审计入口查看已记录的操作、操作者、对象身份、发生时间和可用追溯信息，沿用管理端查询的授权与游标分页；查询失败必须可见，不能解释为空记录。普通工程师查看自身项目版本和业务来源，不因此获得全站审计查询权限。审计查看不提供修改、删除或重新生成记录的能力，也不要求建立新的审计管理平台。

## 开发时怎样选择对象形态

遇到一个新业务数据时，按以下顺序判断：

1. 用户是否需要继续编辑？需要则先设计草稿和 revision；
2. 它是否被任务、结果或审批引用？被引用的形态必须形成不可变版本；
3. 内容是否较大？大内容交给 storage，领域只保存 handle；
4. 丢失后能否从数据库事实重建？可以则属于运行状态或缓存；
5. 是否需要解释历史？需要则保存来源、schema 和依赖版本，而不仅是最终数字。

不要因为数据库表已有 `updated_at` 就把记录视为版本，也不要因为对象带哈希就自动获得业务语义。版本的形成必须对应明确业务动作。

## 典型生命周期

### 数据集上传

```text
创建/选择数据集容器
  ↓ 上传字节到 storage
形成不可变数据版本 + 质量报告 + owner 引用
  ↓ 用户确认
项目草稿绑定明确数据版本
  ↓ 提交任务
CalcSnapshot 固定该绑定与对象引用
```

上传新文件只增加数据版本，不能改变旧绑定和历史任务。

### 项目计算

```text
项目草稿 revision
  ↓ 固化业务版本
项目版本 + 数据版本 + 配置版本
  ↓ assembly
ValidatedAssemblyArtifact → CalcSnapshot
  ↓ Worker attempt / generator
Solver Bundle
  ↓ runtime / result adapter
ExecutionReceipt → Evidence / Result / Assessment / Export
```

每个箭头都应能通过公开 ID 反向追溯。候选方案应用属于新的项目版本动作，不允许原地修改来源版本。

## 增加一个版本化资源

1. 定义草稿、版本和删除/保留状态是否都需要；
2. 明确哪个用户动作创建版本；
3. 选择规范序列化规则；
4. 保存创建者、时间、schema、来源版本和外部依赖；
5. 让数据库约束禁止已发布内容被更新；
6. 定义对象引用的 attach/detach 时点；
7. 测试并发创建、重复提交、历史读取、导出和恢复。

## 完成标准

- 草稿、版本、快照、证据和缓存没有混用；
- 历史资源不依赖当前项目或最新 provider 才能解释；
- 删除、归档、保留和对象清理的关系明确；
- 所有不可变对象都能定位创建动作、来源与版本；
- 前端显示的“版本”能对应一个真实、可查询的领域对象。
