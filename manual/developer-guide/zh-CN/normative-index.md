# 规范索引与文档边界

> 文档状态：生效；适用范围：全部正式文档、内部实施材料、Review 与归档。

本页解决“同一规则写在多处”时应相信哪一处的问题。它不替代任何领域正文；开发者仍应阅读与任务直接相关的完整章节。

## 文档角色

| 位置 | 只负责什么 | 不负责什么 |
| --- | --- | --- |
| [架构宪法](ARCHITECTURE_CONSTITUTION.md) | 跨模块原则、强制边界、冲突裁决 | 版本计划、任务切片、实现进度 |
| 开发者指南其余章节 | 长期目标架构、公共契约、格式与扩展方式 | 开发过程、Roadmap、当前完成状态 |
| 使用者指南 | 已可由产品 GUI 完成的操作与限制 | 内部实现、未来能力 |
| [`manual/changelog/`](../../changelog/README.md) | 已完成事实、产品版本和 Roadmap | 长期架构正文 |
| [`docs/development/`](../../../docs/development/README.md) | 一次实施的交接、测试与发布过程控制 | 产品/架构规则的第二份定义 |
| [`docs/reviews/`](../../../docs/README.md#review) | 带基线的审查证据 | 当前事实或实现规格 |
| [`docs/archive/`](../../../docs/archive/README.md) | 历史追溯 | 任何现行开发输入 |

## 引用与复述

1. 每项稳定规则必须有一个完整的权威正文；其余位置可以为读者复述必要结论，但必须链接该正文的稳定章节。
2. 复述不得重新列出完整字段表、算法参数、例外条件或状态机，除非该页就是该规则的权威正文。
3. 实施材料只写任务范围、明确排除、验证和权威链接；不能以“本次需要”为由创造新的长期字段、默认值或架构边界。
4. 规则发生变化时，先修改权威正文，再检查引用处是否仍准确；不通过复制粘贴同步多份完整规范。

## 立即归档规则

下列任一情况出现时，材料必须在同一次变更中移入 `docs/archive/`，而不是留在现行 `docs/` 入口：

- 已完成或被替代的实施交接、切片计划、旧规格、旧合同、调研或工作流；
- 与现行宪法、开发者指南或 Roadmap 冲突的正文；
- 只能描述历史代码基线、历史评审结论或已废弃设计的材料。

归档前必须先确定现行替代来源；归档文件顶部至少写明状态、归档日期、归档原因和替代来源。随后修复现行入口、必读清单、代码注释和测试说明中的链接。归档原文保持历史证据，不回写成新的现行规范。

## Review 检查项

- 本次修改的稳定规则是否只有一个权威正文？
- 开发者指南是否误写了版本计划、切片或当前进度？
- 内部实施材料是否重复定义了产品契约？
- 是否有已替代的 `docs/` 材料应当即时归档？
- 归档材料的替代来源和现行链接是否已经更新？
