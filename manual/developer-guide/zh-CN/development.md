# 开发、测试与贡献

> 文档状态：生效蓝图；规范版本：1.0.0；上位规范：[架构宪法](ARCHITECTURE_CONSTITUTION.md)

## 变更流程

1. 阅读架构宪法及相关开发者章节。
2. 明确用户场景、公开 contract、失败语义和版本影响。
3. 若修改宪法强制条款，先提交 ADR 并取得明确批准。
4. 先把对应测试迁移到已经批准的目标语义，再实现代码。
5. 只通过公开模块边界完成实现。
6. 提供数据迁移或开发数据重建方案。
7. 同步使用者指南、开发者指南和更新日志。
8. 在 Docker 中运行与风险相称的验证。

历史测试不能迫使实现恢复已经废止的兼容层；删除旧测试时必须说明旧契约及替代覆盖。

## 从零进入一个模块

1. 从[模块开发手册](module-development.md)选择对应章节；
2. 写出上游、公开输入、本模块处理、公开输出和下游；
3. 从模块公开门面和 contract 阅读代码，不先从最长的实现文件开始；
4. 找到现有协议测试，确认当前已经承诺的行为；
5. 把目标变化写成输入输出与失败语义，而不是文件修改清单；
6. 若需要穿透另一个模块，先补对方公开 contract；
7. 完成局部测试后，再接 application、API、Worker 或前端集成。

局部任务应能说明“哪些东西明确不改”。例如修改 finance 指标时，不应同时改变任务租约、HTTP 信封或项目版本语义。

## 实现节奏

```text
用户场景
  ↓
公开 contract 与失败语义
  ↓
模块协议测试
  ↓
模块实现
  ↓
application 集成
  ↓
API / Worker / 前端适配
  ↓
系统验收与文档同步
```

每一步只依赖前一步的公开输出。这样出现问题时可以判断是 contract、模块实现还是集成错误，而不是在端到端测试失败后跨层猜测。

## 测试层次

| 层次 | 主要证明 |
|---|---|
| 纯函数单元测试 | 数值、转换和边界条件 |
| 模块协议测试 | 公开门面、provider、原子发布和失败路径 |
| 文件契约测试 | YAML/CSV schema、规范化、摘要、人工样例和迁移 |
| Generator 测试 | 纯生成、单位、确定性和 Solver Bundle contract |
| Runtime/Adapter 测试 | 命令策略、隔离、资源、状态、输出和结果映射 |
| HTTP 契约测试 | DTO、状态码、权限和错误信封 |
| 持久化测试 | 约束、事务、不可变性和恢复 |
| Worker 测试 | 幂等、租约、重试、超时和迟到写入 |
| 前端测试 | mapper、状态、可访问交互和错误展示 |
| 系统浏览器验收 | 真实用户从页面完成关键流程 |

后端、前端和系统验收保持职责分离。Playwright 可以通过公开接口准备隔离数据，但不能绕过正在验收的 UI 操作。

所有测试都在 Docker 中执行。画布拖放和端口连接由人工核查；画布参数编辑等非拖放功能仍可自动验收。

## 架构门禁

项目应逐步强制检查：

- 不跨模块导入私有符号、loader、repository 或 persistence；
- API 不直接导入 ORM；
- `core` 不依赖业务模块；
- 业务模块不拼对象路径；
- 前端 `shared` 不依赖 feature，页面不直接调用底层 HTTP；
- 前后端没有重复设备、端口、generator/solver 或单位映射；
- 设备/装配文件没有实现入口、shell 或宿主机路径；
- GeneratorProvider 不访问数据库、对象服务、网络或进程；
- 建模命令、runtime 和业务服务没有隐式单位换算；
- runtime 不按设备、generator 或 solver 名称复制业务分支。

## 完成定义

一项功能只有同时满足以下条件才完成：

1. 公开 contract 与版本语义明确；
2. 实现遵守模块边界；
3. 权限、失败和恢复路径已定义；
4. 前后端 contract 与 mapper 同步；
5. 数据迁移或重建方案可执行；
6. Docker 内相关测试通过；
7. 不存在静默兼容、fallback、空数据降级或未管理副本；
8. 正式文档、更新日志与代码一致。

## 变更说明应回答什么

一次可审查的开发变更至少说明：

- 用户或上游调用方得到什么新结果；
- 由哪个模块拥有新规则；
- 输入、输出和失败语义怎样变化；
- 是否影响产品、schema、provider 或文件格式版本；
- 数据与对象生命周期怎样迁移或恢复；
- Docker 中运行了哪些模块、契约和用户流程测试；
- 使用者指南、开发者指南、更新日志或 Roadmap 更新在哪里。

不以“重构了若干文件”“修复了一些问题”代替这些信息。

## 文档贡献

正式正文只写入 `manual/`。Review 放 `docs/reviews/`；已经被替代的资料放 `docs/archive/` 并停止维护。成熟结论应提炼，不复制整份 review。

新增或移动章节时必须同步语言 SUMMARY、修复仓库内链接，并验证帮助中心生成与 Markdown 安全测试。

### 维护分工

| 角色 | 主要责任 | 交付位置 |
|---|---|---|
| 功能负责人 | 写清当前 GUI 流程、失败处理与限制 | 使用者指南、更新日志 |
| 领域或架构负责人 | 维护稳定边界、公共契约和扩展蓝图 | 开发者指南；必要时先提交 ADR |
| Review 负责人 | 记录审查对象、基线、证据和结论 | `docs/reviews/` |
| 发布负责人 | 统一产品版本，整理倒序历史、Roadmap 和发布门禁 | 更新日志、版本化与发布章节 |

同一人可以兼任多个角色，但每项变更必须明确谁负责同步正式文档。Review 中已经成熟的结论由对应领域负责人提炼进入开发者指南，原文不直接变成实现规格。

### 丰满顺序

1. 先在语言 SUMMARY 中确定稳定章节骨架和阅读顺序；
2. 按当前 GUI 补齐使用者任务，不确定或未实现能力进入 Roadmap；
3. 把经宪法裁决的稳定设计意图提炼进开发者指南；
4. 后续开发按版本排入 Roadmap；一项工作实现并验收后，将完成事实写入 `Unreleased`，同时从 Roadmap 删除；
5. 完成链接、内容边界和 Docker 帮助中心验收后，才把本轮文档视为完成。
