# 扩展开发

> 状态：生效架构规则；具体 provider API 随模块迁移逐步发布

## 基本原则

新增设备、算法或存储后端必须实现公开 provider，不得修改无关模块的内部映射表。扩展拥有稳定命名空间 ID 和语义化版本；破坏性 schema 变化提升主版本。

## 设备扩展

设备描述应声明：

- `type_id` 和版本；
- 参数类型、单位、范围、默认值和是否可优化；
- 真实端口 ID、载能类型和方向；
- capabilities、`model_method` 和 `stateful`；
- 所需状态和时间序列字段；
- 对应建模 provider 的公开引用。

前端从公开设备 schema 渲染目录、参数和端口，不为新设备增加硬编码规则。

## 建模与算法扩展

建模命令必须声明稳定 command ID、版本、输入、输出、状态语义和可解析 provider。注册时完整验证函数和依赖，失败则不发布候选注册表。

## 存储扩展

BlobStore adapter 只实现字节保存、读取、删除和健康能力。内容哈希、对象元数据、owner 引用和生命周期由 storage 服务统一管理；业务模块不能感知文件系统、S3 路径或 adapter 凭证。

## 验收

扩展测试必须证明：

- 新扩展无需修改前端或其他模块的类型映射；
- 启动时 ID、版本和依赖可解析；
- 构建失败不产生部分注册状态；
- 输入输出、单位和错误符合公开 contract；
- 所有编译和测试只在 Docker 中运行。
