# 扩展体系

> 文档状态：生效蓝图；规范版本：1.0.0；上位规范：[架构宪法](ARCHITECTURE_CONSTITUTION.md)

## 总体模型

设备、建模命令、计算生成器、执行器、结果适配器、存储和可选数据来源通过各自模块的公开 provider 接入。每个模块独立拥有注册状态；不存在跨模块全局注册表。

扩展在启动时发现和注册。正式发布前不支持运行期热加载。候选集合必须完整构建、验证并一次性发布；任一必需项失败时实例不得进入 ready，也不得继续使用静态 fallback。

网页“模型与算法”是用户扩展入口，但不改变 provider 的启动注册原则。设备模型 YAML 是版本化声明内容；算法插件 ZIP 是交给系统内置通用沙箱 generator/executor/result adapter 的不可变任务载荷。上传插件不会把用户模块加入 API、普通 Worker 或 provider 注册表，因此可以在校验成功后进入所有者目录，不需要管理员批准。只有申请进入共享园地时需要管理员审批。详细生命周期见[模型与算法](customization-center.md)。

## 共同元数据

每个扩展至少声明：

- 稳定命名空间 ID；
- 三段式语义版本；
- 所需产品公共契约版本；
- 能力清单和依赖；
- 输入、输出与 schema 版本；
- 单位、错误和本地化消息键；
- 确定性、随机种子和资源要求；
- 契约测试、参考输入、参考输出和容差；
- 许可证、供应者和迁移说明。

稳定 ID 不包含部署路径或实现类名。破坏性 schema 变化必须提升扩展主版本，并保证历史快照仍能解析或有明确保留策略。

## 设备 provider

设备公开描述至少包含：

- 设备类型 ID、名称和版本；
- 参数类型、规范单位、范围、默认值和可优化标记；
- 真实端口 ID、载能类型、方向和连接语义；
- 能力、状态、所需时序字段与模型方法；
- 对建模命令的公开引用。

前端按公开描述呈现设备、参数和端口。增加设备不能要求前端或其他模块新增类型判断表。

设备的文件交付格式固定为 [设备模型 YAML](formats/device-model-yaml.md)；时序样例按[设备数据 CSV](formats/device-data-csv.md)提供。目录路径、Python 包入口和实现类名不是公共身份。

## 建模命令 provider

建模命令声明稳定命令 ID、版本、输入、输出、状态语义和所需设备能力。它把一个设备实例变成声明式变量、约束、目标项和结果映射元数据，不启动求解器，也不返回某个求解器的私有对象。

装配阶段验证设备、命令、generator 和 solver 版本是否能够协作；任务快照固定实际使用的版本。缺少命令或能力不匹配必须在执行前失败。

## 计算 provider

计算扩展拆成三个主要角色：

- GeneratorProvider：只接受 `ValidatedAssemblyArtifact`，生成 [Solver Bundle](formats/solver-bundle.md)；
- ExecutorProvider：把受信任 executable ID 映射为受控进程或容器执行方式；
- ResultAdapterProvider：把声明输出和执行回执映射为统一 `ComputeResult`。

GeneratorDescriptor 必须提前声明支持的装配 schema、计算 mode、命令能力、solver、选项、内部单位、确定性和配套 ResultAdapter。ExecutorDescriptor 必须声明 allowlist、资源隔离、取消和 readiness 能力。运行时只执行结构化命令；provider 不得要求用户在装配 YAML 中写 shell 或代码路径。

具体开发流程见[计算生成器](modules/generators.md)和[求解运行时](modules/solver-runtime.md)。

## 存储 provider

存储适配器只实现字节级保存、读取、删除和健康能力。内容摘要、对象元数据、引用、配额、保留和恢复由 `storage` 领域统一管理。

业务模块不能感知文件系统或对象服务路径，也不能持有 adapter 凭证。更换存储 provider 不应修改项目、数据集、结果或前端契约。

## 数据 provider

外部气象、价格或排放数据只能生成可审计的候选数据版本。数据必须先经过单位、时区、分辨率、缺失值、范围和来源检查，再由用户确认并绑定；GeneratorProvider 和 SolverRuntime 不能在运行时直接依赖外部服务。

## 扩展验收

每类扩展必须证明：

- 新增扩展不修改无关模块的映射；
- 启动时 ID、版本、依赖和能力可解析；
- 构建失败不污染已发布状态；
- 输入、输出、单位和诊断符合公共契约；
- 历史任务固定版本后可解释；
- 所有测试在 Docker 中执行。

从网页或 API 上传扩展时还必须证明：归档解包不能路径逃逸或携带符号链接；用户代码不会被 API 或普通 Worker import、执行或加入 `sys.path`；静态校验和动态自检只在隔离运行器发生；校验报告和对象摘要可追溯；目录状态与实际可运行状态不一致时显示“不可用”，不得回退到同名内置实现。

具体 SDK、签名和可运行样例只有在公共接口稳定后才发布；Roadmap 中的目标不能提前写成已可用接口。

## Provider 开发流程

1. 先选择所属模块和单一 provider 角色，不创建跨设备、生成、执行和存储的“万能插件”；
2. 阅读对应[模块开发手册](module-development.md)，确定输入输出和失败语义；
3. 选择稳定命名空间 ID 与三段式扩展版本；
4. 实现公开 Protocol，并把环境依赖封装在 provider 内；
5. 提供 descriptor、能力、配置 schema 和健康检查；
6. 使用所属模块的统一契约测试集验证；
7. 在组合根注册候选，验证依赖后原子发布；
8. 用一个外部测试扩展证明核心模块和前端无需修改。

扩展开发者不应先在 API 或 GUI 增加类型分支，再倒推 provider 形状。正确顺序是先让领域 descriptor 足以表达能力，消费者随后按公开 schema 通用呈现。

## 输入与输出的自描述要求

Provider 不能只提供一个 callable。调用方在执行前必须能读取：

- 它是谁、是什么版本、兼容哪个 contract；
- 它接受哪些字段、单位、形状和状态；
- 它产出哪些字段、单位、状态和诊断；
- 它是否确定、怎样传随机种子、需要什么资源；
- 它依赖哪些其他公开 ID 和最低版本；
- 它怎样报告健康、不可用和配置错误。

这些元数据用于启动校验、装配、快照和历史解释，不能只存在于实现注释。

## 兼容与升级

- 兼容增加可选能力提升扩展 MINOR；
- 修复不改变 contract 的缺陷提升 PATCH；
- 删除/改名字段、改变单位或状态语义提升扩展 MAJOR；
- 产品升级不能机械修改所有扩展版本；
- 任务快照固定实际版本，升级后仍需能解释旧证据；
- 无法继续执行旧版本时，应提供保留读取或明确迁移，而不是调用最新实现猜测。

## 故障排查思路

Provider 未进入 ready 时，按“发现 → 配置 → contract 校验 → 依赖解析 → 原子发布”逐层定位。日志应指出 provider ID、版本和失败阶段，但不输出凭证或内部数据。不要捕获异常后改用内置 provider，这会让部署配置和实际执行版本不一致。

## 完成标准

- 扩展包可以只依赖公开 contract 和文件 schema 开发；
- 核心仓库无需增加扩展 ID 判断；
- 合法与非法 provider 都通过统一协议测试验证；
- 启动、快照、结果和运维状态显示实际扩展版本；
- 升级、缺依赖和失败不会留下部分注册状态。
