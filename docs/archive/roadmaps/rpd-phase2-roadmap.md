# pIES 产品版本 2 Roadmap

- 制定日期：2026-08-20
- 最后更新：2026-08-21
- 依据：`IES-Plan-Design-Input.rpd`、`docs/rpd-implementation-gap-review.md`
- 适用范围：产品版本 2 / 二阶段
- 文档状态：路线图草案，用于范围、依赖和交付顺序管理

---

## 1. Roadmap 目标

产品版本 2 在不破坏版本 1 核心不变量的前提下，扩展以下能力：

1. 扩充设备和能源系统建模范围；
2. 建立设备模型、建模命令和求解算法的版本化插件开发与替换能力；
3. 提供问答式信息收集，降低建模和参数配置门槛；
4. 提供 AI 辅助报告生成；
5. 提供 AI 辅助 Excel 标准化；
6. 支持本地 Open WebUI 等本地 AI 服务对接；
7. 继续保持项目版本、数据版本、计算快照和结果证据的可追踪性；
8. 不把版本 2 扩展成生产实时调度、设备控制或浏览器内正式求解系统。

### 1.1 二期范围

根据 RPD，二期原始范围包括：

- 风电；
- 燃气内燃机；
- 余热锅炉；
- 吸收式制冷机；
- 热储能；
- 冷储能；
- 问答式信息收集；
- AI 报告生成；
- AI Excel 标准化；
- 本地 Open WebUI 对接。

本路线图新增：

- **模型与算法插件化**：设备模型、标准建模命令和求解算法通过各自的公开契约、独立 Registry 和版本化 Provider 开发、注册与替换；任务快照固定实际使用的插件 ID、版本和参数。
- **典型工况与规划—运行闭环**：建立典型时段识别、容量规划、全年逐时运行校核、偏差自适应重算和多目标方案比较闭环。
- **市场场景与柔性资源建模**：支持用于规划仿真的历史/预测电价场景和可调负荷/需求响应，不扩展为实时交易、运行调度或控制下发。
- **外部数据 Provider（可选）**：气象、价格或排放因子等外部 API 不再作为二期主线，只能以受控数据 Provider 接入，输出可追溯的候选数据版本，不得成为计算引擎的运行期依赖。

### 1.2 明确不属于二期默认范围

以下内容不因二期扩展自动纳入：

- 实时生产运行计划；
- 实时调度；
- 设备控制或控制指令下发；
- 浏览器内正式求解；
- 外部身份提供方和外部角色自动映射；
- 未经注册、测试和权限隔离的任意第三方插件；
- 正式发布前的运行期热加载、热替换或部分注册状态；
- 把可选外部数据 Provider 返回结果直接作为不可追踪的权威输入；
- 让 AI 直接修改项目权威数据或直接提交计算任务而不经过确认。

## 2. 现状与路线图原则

### 2.1 版本 1 审查中发现的前置问题

二期不应直接建立在当前所有问题之上。以下版本 1 问题必须在相应二期能力上线前修复或明确降级：

- 不确定性参数从前端到 Worker 的链路断裂；
- 失败样本可能被计为有效样本；
- 规划层目前是容量枚举/抽样加逐候选评价，不是完整规划级 MILP/MINLP；
- 多目标和 Pareto 计算尚未形成真实闭环；
- 工程参数、设备寿命、网络约束和财务结果部分未闭环；
- 结果页和 Excel 存在使用当前版本而不是计算快照版本的追踪风险；
- 永久版本的前端创建/恢复入口不完整；
- I/O Worker 仍有占位执行器；
- 数据库迁移、部署迁移和恢复验证入口不足；
- 用户数量、同时在线人数、CSRF、资源限制和最低分辨率提示尚未完成系统验收。

### 2.2 二期核心原则

1. **先计算正确性与扩展契约，后 AI 和外部服务。**
2. **`devices` 拥有设备 Registry，`modeling` 拥有建模命令/算法 Registry，禁止全局跨模块注册表。**
3. **插件候选集必须完整构建、校验后一次性发布，失败时不发布新状态。**
4. **设备模型扩展与求解算法扩展分开交付，通过公开建模命令协作。**
5. **AI 产出默认是建议、草稿或待审核结果，不直接改变权威项目状态。**
6. **每个新设备必须有数据、单位、方程、约束、财务和验证案例。**
7. **每个插件必须有稳定 ID、语义化版本、能力声明、契约测试和参考案例。**
8. **每个阶段都必须有可独立验收的垂直切片，不以“所有二期功能完成”作为唯一交付节点。**
9. **外部数据只能作为可审计的候选输入，不能绕过数据版本、质量门禁和计算快照。**

## 3. 总体顺序

建议按以下顺序推进：

```text
P0：版本1收口与规划—运行闭环
        ↓
P1：模型与算法插件化基础设施
        ↓
P2：新增设备、柔性资源与市场场景扩展
        ↓
P3：问答式信息收集
        ↓
P4：AI Excel标准化
        ↓
P5：AI报告生成
        ↓
P6：本地Open WebUI对接与统一AI编排
        ↓
P7：二期整体验收、迁移和发布
```

其中：

- 规划算法必须先完成“典型工况容量规划 → 全年逐时运行校核 → 偏差超限重算”闭环，再对外宣称智能容量规划；
- 插件契约先于二期设备和算法扩展，新模型不得以引擎内部硬编码分支接入；
- 新增设备模型应先于依赖这些设备的问答、报告和 Excel 生成；
- 气象、电价和排放因子可由用户上传或可选数据 Provider 提供，核心计算不得依赖外网可用性；
- AI Excel 标准化应先于 AI 报告生成，因为报告需要依赖标准化后的数据和质量结论；
- 本地 Open WebUI 对接放在 AI 能力稳定后，避免同时调试模型服务、业务提示词和基础数据契约。

# 4. 阶段 P0：版本 1 收口与规划—运行闭环

## 4.1 目标

在二期开发前，先把版本 1 的结果正确性、版本追踪和部署边界收口，并将计算规格中已定义的典型工况容量规划与全年运行校核实现为可验收闭环。

## 4.2 必须完成的工作

### 计算正确性

- 修复不确定性任务参数结构不一致；
- 统一 `distribution` / `distributions` 字段；
- 明确任务种子与计算快照种子的优先级；
- 修复失败样本状态、有效样本数和统计分母；
- 对样本级取消、重试、恢复和部分完成建立可测试语义。

### 结果与版本追踪

- 结果页使用计算快照绑定的项目版本和数据版本；
- Excel 使用 `snapshot.project_version_id`，禁止读取项目当前版本代替历史输入；
- 项目包、Excel、结果页统一使用同一份快照元数据；
- 补齐永久版本创建、查看和恢复的前端入口。

### 求解和结果状态

- 明确规划层枚举/抽样的降级语义；
- 补充可行性、停止原因、Gap、未证明最优、数值失败等状态；
- 明确单目标与多目标当前版本边界；
- 为新增设备、建模命令、求解算法和数据 Provider 建立分属模块的公开注册契约。

### 典型工况与容量规划

- 建立对辐照、气温、风速、电/热/冷负荷和电价的联合特征规范；
- 实现可复现的典型日/典型时段聚类，默认可使用 K-means，但聚类算法必须通过算法 Provider 选择；
- 强制保留峰值负荷、极端温度、低可再生供给和极端电价时段，禁止只保留聚类中心而丢失设计边界；
- 产出不可变的代表性时段集，记录特征版本、标准化规则、算法 ID/版本、随机种子、聚类权重和质量指标；
- 以代表性时段集实现完整容量规划 MILP，支持容量、建设选择、运行约束和最低 IRR 等硬约束；
- 完成加权法、优先级法、ε-约束法与 Pareto 支配过滤的真实计算闭环；
- 当完整 MILP 未实现或不可用时，枚举/抽样只能作为明确标记的降级算法，不得报告为已证明最优。

### 全年运行校核

- 对最终候选方案固定容量后执行全年逐时运行优化和费用精算；
- 强制校验能量平衡、设备出力、启停、储能状态、弃风弃光、负荷削减和并网约束；
- 比较典型时段加权结果与全年校核的费用、排放、弃电和储能循环偏差；
- 偏差超过可配置门限时，增加代表性时段并重新规划，保留每轮输入、结果和停止原因；
- 将规划结果、全年校核和偏差报告统一绑定到计算快照与证据对象。

### 场景、敏感性与稳定性分析

- 将当前单因子扫描扩展为可追溯的场景矩阵和多参数批量分析；
- 对电价、负荷、气象、设备投资和运维成本输出变化率、影响排序、单调性和极值点；
- 对重规划结果输出设备选型频率、容量分布、容量不稳定指数和后悔值；
- 产出可供前端表格、龙卷风图、场景对比和报告引用的版本化结构化证据；
- 无效、失败和未完成样本必须与有效样本隔离，报告完成率和统计分母。

### 运维和安全

- 完成数据库迁移和部署迁移入口；
- 验证对象存储、数据库和项目包恢复流程；
- 明确 Redis 不可用时的登录限速策略；
- 补齐 CSRF、用户数/在线数门禁和最低分辨率提示；
- 建立 Docker 级并发、资源限制、超时和孤儿进程验收。

## 4.3 退出标准

- 版本 1 关键验收不再存在已知的结果快照错配；
- 不确定性测试能够证明参数生效、无效样本隔离、统计分母正确；
- 版本、数据、快照、证据包和导出之间可互相追踪；
- 迁移、备份、恢复和 Docker 部署有可重复操作入口；
- 二期扩展契约已经冻结并有自动化校验；
- 典型工况、容量规划、全年运行校核和偏差自适应重算可在同一快照链路中追溯；
- 至少一个小型可手算案例和一个代表性工程案例通过规划—运行偏差门禁；
- 多目标结果能输出真实 Pareto 候选、不可行网格点和每点求解状态。
- 场景、敏感性和稳定性结果能追溯到每个输入版本、快照、样本状态和计算尝试。

# 5. 阶段 P1：模型与算法插件化基础设施

## 5.1 目标

建立可开发、可校验、可选择和可替换的扩展机制，使新设备模型、数据驱动/机理建模命令与求解算法无需修改跨模块内部实现即可接入系统。

插件化必须保持模块自治，不建立全局万能插件表：

```text
插件包/内置 Provider
    ↓ 发现候选项
设备 Registry / 建模命令与算法 Registry
    ↓ 契约、版本、依赖与能力校验
组合根一次性发布完整状态
    ↓
装配边界生成 ComputePlan
    ↓
任务快照固定插件 ID、版本、配置和摘要
```

## 5.2 插件类型与责任边界

### 设备模型 Provider

- 声明设备稳定 ID、语义化版本、参数、单位、端口、能力、状态和支持的建模方法；
- 通过 `devices` 公开契约注册，禁止访问项目 ORM、画布布局或前端展示状态；
- 同一稳定 ID 的破坏性 schema 变化必须提升主版本；
- 替换设备 Provider 只影响新项目版本或明确重新计算，不重写历史快照和结果。

### 建模命令 Provider

- 声明标准 `ModelCommand` 的输入 schema、输出 schema、所需设备能力、确定性、随机种子和版本；
- 可接入机理模型、数据驱动模型、典型工况生成器和其他标准建模函数；
- 只能消费设备模块公开 descriptor/provider，不得读取设备目录内部路径或 Registry 实现；
- 输出必须经过装配与单位边界，不得直接构造绕过检查的引擎输入。

### 求解算法 Provider

- 声明算法 ID、版本、支持的问题类型、变量/约束能力、多目标能力、最优性证明能力、随机性和资源要求；
- 首批以 MILP/固定容量运行优化为权威实现，枚举、抽样、遗传算法或粒子群只能在完成基准验证后作为可选 Provider；
- 算法选择必须在任务提交前根据问题能力进行显式匹配，不允许引擎内部宽异常回退到默认算法；
- 运行中必须输出状态、停止原因、Gap/边界、耗时、随机种子和算法特有证据。

### 数据 Provider（可选）

- 用户上传始终是核心数据入口，气象、能源价格和排放因子等外部 API 只是可选数据 Provider；
- 数据 Provider 使用独立契约和白名单，不与 `devices` 或 `modeling` Registry 合并；
- 外部响应必须先形成原始对象和待确认数据版本，经单位、时区、分辨率、缺失值和范围校验后才能绑定快照；
- 外部网络不可用不得影响已绑定数据和核心计算。

## 5.3 插件包、发现与生命周期

每个插件包至少提供：

- 插件包 ID、版本、供应方和许可信息；
- 所提供的设备、建模命令或算法清单；
- 对 pIES 公开契约版本和其他插件的依赖声明；
- 输入/输出 schema、单位、诊断和本地化 key；
- 契约测试、参考数据集、参考结果和容差；
- 迁移规则、已知限制和资源要求。

生命周期规则：

- 组合根只负责发现 Provider、完成依赖注入和启动校验，不建立新的全局权威表；
- 候选 Registry 必须完整构建和校验后一次性发布，任一必需 Provider 失败则启动失败或实例不 ready；
- 正式发布前不实现运行期热加载；升级或替换通过安装新版本、Docker 内验证和重启实例生效；
- 同一任务和快照始终使用已固定的插件版本，不随当前已安装版本变化；
- 删除或升级插件前必须检查历史快照、证据和项目版本的可读性与保留策略。

## 5.4 开发、安装与替换工作流

1. 从公开 SDK/示例模板创建插件；
2. 在 Docker 内执行 schema、单位、契约、架构边界和参考案例测试；
3. 管理员安装并启用指定版本，组合根在启动时校验完整注册状态；
4. 项目或计算配置从能力匹配后的候选项中显式选择模型/算法；
5. 装配门禁校验设备、建模命令、算法、参数和版本能否协同；
6. 提交任务时将选择结果固定到不可变快照；
7. 替换插件时生成新项目修订/计算快照，并提供同一输入下的结果差异报告；
8. 任何缺失、不兼容或损坏插件都必须显式失败，不得回退到内置静态映射或默认算法。

## 5.5 退出标准

- 至少一个外部设备模型 Provider 能在不修改核心模块内部映射的情况下完成注册、装配、计算和导出；
- 至少两个求解算法 Provider 能对同一公开计算命令进行能力匹配、显式选择和结果差异比较；
- 替换模型或算法后新任务使用新版本，历史快照和结果仍保留原版本证据；
- 未注册、版本不兼容、能力不匹配或测试失败的插件不能进入 ready 状态；
- 插件不能访问其他模块的内部 Registry、repository、ORM、对象路径或用户会话；
- 可选数据 Provider 断网或失败时，用户上传数据、已绑定数据版本和核心计算仍可使用。

# 6. 阶段 P2：二期设备、柔性资源和市场场景扩展

## 6.1 目标

在 P1 的公开插件契约、独立 Registry、数据契约和验证体系上，增加 RPD 二期设备、柔性资源和规划使用的市场场景，而不是仅增加前端卡片或引擎内部分支。

## 6.2 建议设备交付顺序

建议按能量耦合复杂度和依赖关系排序：

### P2-A：热储能和冷储能

优先原因：

- 与电池储能具有相似的 SOC/容量/充放约束结构；
- 可以先验证储能通用接口；
- 可复用周期边界、损耗、功率上限和容量约束框架。

必须覆盖：

- 热/冷能量状态；
- 充放热/冷功率；
- 充放效率；
- 自放热/冷损失；
- 温度或可用容量边界；
- 初始和终止状态；
- 设备寿命和更换；
- 与热泵、锅炉、电制冷机和负荷的连接规则。

交付边界：

- 首先实现通用热/冷储能契约；
- 水蓄热、熔盐储热等工程形态以不同设备 Provider 扩展，不将单一介质硬编码为全局储热模型。

### P2-B：风电

依赖：

- 用户上传的风资源数据，或经确认的可选气象数据 Provider 版本；
- 统一时序数据校验；
- 风速到功率曲线转换；
- 并网和弃风约束。

必须覆盖：

- 风速高度和测量条件；
- 功率曲线版本；
- 切入、额定和切出风速；
- 机组可用率；
- 额定容量和并网容量；
- 弃风、限发和反送限制；
- 设备投资、运维和寿命。

### P2-C：燃气内燃机

依赖：

- 燃气价格和排放因子数据；
- 电热联供能流接口；
- 启停和最小出力逻辑。

必须覆盖：

- 电效率；
- 余热回收效率；
- 最小/最大出力；
- 启停状态；
- 最小开停机时间；
- 燃气消耗；
- 排放；
- 维护和启停成本；
- 与余热锅炉、热负荷和电负荷的耦合。

### P2-D：余热锅炉

依赖：

- 燃气内燃机或其他余热源的热流接口；
- 热网和热负荷模型。

必须覆盖：

- 余热输入；
- 热回收上限；
- 热效率；
- 最低稳定出力；
- 热水/蒸汽等介质定义；
- 热损失；
- 与燃气锅炉和热泵的互斥/协同约束。

### P2-E：吸收式制冷机

依赖：

- 余热锅炉或热源设备；
- 冷网传输和冷负荷模型；
- COP 与热源温度语义。

必须覆盖：

- 热驱动制冷；
- COP 或性能曲线；
- 最小稳定出力；
- 热源不足时的可用性；
- 冷量上限；
- 冷却水/泵耗电；
- 与电制冷机的协同和切换。

### P2-F：可调负荷与需求响应

依赖：

- 负荷基线、生产/舒适性约束和用户明确授权；
- 逐时运行优化、事件时间窗和补偿成本语义；
- 用于规划仿真的价格/需求响应场景版本。

必须覆盖：

- 可转移负荷的时间窗、能量守恒和最大转移量；
- 可中断负荷的最大削减量、持续时间、事件次数和补偿成本；
- 削减后的负荷恢复/反弹效应；
- 工业班次、最小连续运行时间、产量或建筑舒适度边界；
- 用户可见的服务成本、补偿收益、违约风险和实际调整事件；
- 与“供应不足时的惩罚性负荷削减”使用不同设备/命令契约和结果字段，禁止混用。

## 6.3 市场与预测场景数据

市场数据只服务于容量规划、任意方案评价和不确定性分析，不产生实时报价、交易或控制指令。

必须覆盖：

- 分时目录电价、历史现货价格、预测价格和实际结算价使用不同数据类型；
- 支持逐时或 15/30/60 分钟购售电价序列、负电价和尖峰价格；
- 记录市场区域、交易品种、币种、时区、预测发布时间和适用时间范围；
- 建立基准、高波动、极端峰价、负电价、源荷预测偏差等不可变场景集；
- 实际值、预测值和人工假设必须具有不同来源与质量状态；
- 计算任务必须绑定具体场景版本，禁止使用“最新价格”重新解释历史结果。

## 6.4 统一计算要求

每个新设备必须同步实现：

- Registry 声明；
- 插件包清单、稳定 ID、语义化版本和依赖声明；
- 参数和单位；
- 端口和连接校验；
- 时序运行模型；
- 规划变量和约束；
- 财务 CAPEX/OPEX；
- 排放和工程指标；
- 不确定性分析支持；
- 导入导出 schema；
- 诊断和错误文案；
- 合成案例；
- 代表性工程案例；
- 参考结果和容差。

## 6.5 退出标准

- 每种设备都有至少一个可手算或可枚举的确定性案例；
- 每种设备至少有一个与其他设备耦合的案例；
- 三种数据分辨率都能保持同一单位和结果语义；
- 新设备能进入项目版本、计算快照、结果、Excel 和项目包；
- 不确定性分析能正确扰动新设备相关输入；
- 设备新增不会破坏版本 1 项目的读取和重新计算。
- 可调负荷与惩罚性负荷削减能在契约、优化和结果中明确区分；
- 历史/预测电价、负电价和极端价格场景可重现，且断网时仍可使用已绑定版本；
- 二期设备和柔性资源均以 P1 插件契约接入，核心引擎不新增按设备类型分支的静态映射。

# 7. 阶段 P3：问答式信息收集

## 7.1 目标

将复杂的建模、数据和参数配置转化为有上下文的问答流程，但最终仍生成可审计的项目草稿和待确认命令。

## 7.2 功能范围

- 根据项目类型、能源需求和现有设备生成问题清单；
- 分阶段收集：
  - 项目基本信息；
  - 地理位置和气象需求；
  - 电/热/冷负荷；
  - 存量设备；
  - 新建设备；
  - 经济和财务假设；
  - 可靠性和规划偏好；
- 对缺失信息给出“必填、建议、可跳过”分类；
- 将答案映射为草稿变更预览；
- 根据已注册设备、建模命令和算法的能力 schema 生成候选模型与算法推荐；
- 展示每个推荐的适用条件、未满足前提、替代项和预计资源需求；
- 显示单位、范围、来源和不确定性；
- 支持用户逐项确认、修改和撤销；
- 支持从已有项目模型反向生成问答上下文；
- 提供中英文一致的术语和错误提示。

## 7.3 与 AI 的边界

- 问答引擎可以提出问题和建议默认值；
- AI 可以解释为何推荐某个已注册模型/算法，但推荐候选集和能力匹配结果必须由结构化 schema 决定；
- AI 不直接写入项目权威版本；
- 所有变更必须经过用户确认；
- 外部数据 Provider 返回的信息必须显示来源、Provider 版本和获取时间；
- 不确定信息不能伪装为用户已确认的工程参数；
- 问答过程需要保留版本、回答、来源和最终采纳状态。

## 7.4 依赖

- P0 的草稿命令和永久版本闭环；
- P1 的设备/建模/算法插件契约与能力发现；
- P2 的设备、柔性资源、市场场景和参数 schema；
- 可选数据 Provider 的数据版本和质量报告；
- 统一单位、错误文案和帮助元数据。

## 7.5 退出标准

- 用户可从空项目完成一条端到端问答流程；
- 每个回答都能追溯到生成的草稿变更；
- 用户拒绝或修改建议后，不会留下隐式写入；
- 模型/算法推荐不会超出当前已注册能力，且用户可查看推荐理由和替代项；
- 外部数据来源、AI 建议和用户确认状态可区分；
- 断网时仍可完成不依赖外部服务的问答流程。

# 8. 阶段 P4：AI Excel 标准化

## 8.1 目标

将格式不统一、字段名不一致或存在轻微结构差异的用户 Excel 转换为系统可校验的数据集草稿，并保留原始文件和转换证据。

## 8.2 功能范围

- 识别工作表、表头、合并单元格和数据区域；
- 识别中英文列名和常见同义词；
- 识别时间列、负荷列、电价列、温度列、辐照列等；
- 识别单位并提出单位转换建议；
- 识别时间分辨率和固定 UTC 偏移；
- 检查缺失值、重复值、乱序、异常范围和列类型；
- 生成标准化预览和差异报告；
- 支持用户逐列确认；
- 确认后生成新的数据集版本；
- 原始 Excel、标准化结果、映射规则和质量报告均可导出。

## 8.3 安全和质量要求

- 原始文件只读保存；
- 公式、宏、外部链接和嵌入对象默认不执行；
- 不能通过 Excel 内容触发任意代码或任意网络请求；
- AI 识别结果必须有置信度和待确认状态；
- 标准化失败必须定位到工作表、行、列和单元格；
- 标准化结果不能绕过数据集校验门禁；
- 不能把 AI 推断的值标记为原始事实。

## 8.4 依赖

- 可选数据 Provider 的数据引用 schema；
- P2 设备和数据字段注册；
- 版本 1 已完成的数据集校验、对象存储和项目包机制；
- 问答式信息收集可复用字段确认组件。

## 8.5 退出标准

- 至少覆盖三种常见 Excel 模板差异；
- 标准化结果必须经过同一套数据质量校验；
- 用户可以逐项接受、拒绝和修改 AI 映射；
- 生成的数据集版本可用于计算并能回溯原始文件；
- 离线部署下仍可使用规则型标准化，AI 能力不可用时有明确降级提示。

# 9. 阶段 P5：AI 报告生成

## 9.1 目标

基于已完成且可追踪的计算结果、工程指标、财务指标和质量状态生成双语报告草稿，减少人工整理，但不改变权威结果。

## 9.2 报告内容

- 项目和计算快照摘要；
- 输入数据和可选外部数据 Provider 引用清单；
- 设备模型、建模命令、求解算法的插件 ID、版本和能力摘要；
- 模型、设备和主要假设；
- 规划目标、约束和算法；
- 求解状态、Gap、停止原因和适用范围；
- 财务指标；
- 运行、排放和工程指标；
- 可靠性分析统计和无效样本说明；
- Pareto 候选和用户选择；
- 候选方案推荐理由、起主导作用的约束和与次优方案的差异；
- 典型工况与全年运行校核的费用、排放、弃电和储能循环偏差；
- 电价、负荷、气象、投资成本的敏感性排序、容量稳定性和后悔值；
- 风险、缺失数据和待确认事项；
- 结果局限性和不应作出的运行控制解释。

## 9.3 生成规则

- 以结果证据包和计算快照为唯一事实来源；
- AI 只能重述、归纳和解释已存在的结构化结果；
- 约束主导性、边际影响、敏感性和方案差异必须由求解/分析模块产生结构化证据，禁止 AI 自行猜测原因；
- 所有数字必须引用来源字段；
- 缺失或不确定值必须明确标注；
- 不允许 AI 自行补造数据、结论或经济假设；
- 报告为草稿，用户确认后才能导出正式版本；
- 报告记录使用的模型、提示模板、AI Provider 和版本；
- 支持重新生成，并保留不同报告版本。

## 9.4 依赖

- P0 的快照和结果追踪修复；
- P1 的模型/算法插件清单和版本证据；
- 可选外部数据 Provider 的引用清单；
- P2 的设备和工程指标；
- 可靠性和多目标结果状态完整；
- P4 的数据质量和标准化结果。

## 9.5 退出标准

- 报告中的每个关键数字都能定位到结果证据；
- 每个推荐理由、主导约束和敏感性结论都能定位到结构化分析证据；
- 失败、不可行、低质量和未证明最优结果不会被描述为成功方案；
- 中英文报告结构和关键术语一致；
- AI 服务不可用时仍可导出结构化非 AI 摘要；
- 报告生成不会修改项目版本、计算快照和原始证据。

# 10. 阶段 P6：本地 Open WebUI 对接与统一 AI 编排

## 10.1 目标

支持用户在本地部署的 Open WebUI 或兼容 OpenAI API 的本地模型服务上运行问答、标准化辅助和报告生成，降低数据离开本地部署环境的风险。

## 10.2 对接范围

- 可配置本地 AI endpoint；
- 支持 OpenAI-compatible chat/completions 等最小能力；
- 管理员启用/禁用本地 AI Provider；
- 连接测试和模型能力发现；
- 请求超时、重试、限流和取消；
- Provider 不可用时回退规则引擎或结构化摘要；
- 支持按功能选择不同模型；
- 明确上下文长度、文件上传和工具调用能力。

## 10.3 数据边界

- 默认只发送用户明确选择的项目数据；
- 支持脱敏、字段白名单和上下文预览；
- 禁止默认发送密码、API Key、会话凭证和未授权项目；
- 本地 Provider 与外部云 Provider 使用不同的信任级别；
- 请求和响应保存内容哈希及元数据，敏感正文按配置保留；
- AI 不直接执行数据库写入、文件系统访问或外部网络请求。

## 10.4 依赖

- P1 的版本化 Provider、能力发现和快照追踪机制；
- P3 问答协议；
- P4 标准化输入输出；
- P5 报告生成模板和证据引用；
- 部署环境网络边界和离线降级机制。

## 10.5 退出标准

- 本地 Open WebUI 可独立完成问答和报告草稿生成；
- 用户能看到发送给模型的上下文摘要；
- 本地 AI 不可用时核心版本 1 功能不受影响；
- 本地和外部 Provider 的权限、审计和数据边界可区分；
- AI 产出仍必须经过用户确认，不改变权威项目状态。

# 11. 阶段 P7：二期整体验收与发布

## 11.1 端到端场景

至少覆盖以下完整场景：

1. 安装一个外部设备模型插件和一个可替换求解算法插件，通过启动校验后显式选择使用；
2. 用户通过问答创建包含风电、电池和可调负荷的项目；
3. 使用用户上传气象数据，并可选使用数据 Provider 生成待确认数据版本；
4. 用户上传并通过 AI 标准化负荷和历史/预测电价 Excel；
5. 生成典型工况，完成容量规划、全年逐时运行校核和偏差超限重算；
6. 使用燃气内燃机、余热锅炉、吸收式制冷机和冷/热储能构建冷热电系统；
7. 比较至少两个求解算法 Provider 的能力、状态、结果和资源消耗；
8. 查看 Pareto 前沿、市场场景、可靠性、敏感性、容量稳定性和后悔值；
9. 生成带插件版本、数据来源、快照、推荐理由和质量状态的双语 AI 报告；
10. 将项目包和 Excel 导出后在离线部署中恢复，并通过本地 Open WebUI 重新生成报告草稿；
11. 升级或替换模型/算法插件后重新计算，确认历史结果仍保持原插件版本和追踪关系；
12. 禁用可选数据 Provider 和 AI 服务，确认用户上传数据、已绑定数据和核心计算仍可用。

## 11.2 必须验证的不变量

- 项目版本和计算快照不可变；
- 任务绑定的设备、建模命令和求解算法插件 ID/版本不可变；
- `devices` 与 `modeling` Registry 保持模块自治，不出现全局可变注册表；
- 可选外部数据引用不能绕过数据版本和质量门禁；
- AI 产出不能直接成为权威项目状态；
- 外部数据、AI 建议、用户确认和计算输入可区分；
- 历史结果不会被当前项目版本或最新数据版本污染；
- 项目包导入创建新项目身份，原授权关系不迁移；
- 可选数据 Provider 失败不破坏离线能力；
- 新设备未通过验证时不能进入生产 Registry；
- 插件替换不重写历史快照、证据和结果；
- 失败、不可行、低质量和未证明最优状态不会被报告为成功；
- 凭证、敏感信息和未授权项目不会泄露给外部服务。

## 11.3 发布门禁

### 功能门禁

- 所有二期设备完成模型、校验、计算、结果和导出闭环；
- 典型工况、容量规划、全年运行校核、偏差重算和 Pareto 结果形成可追溯闭环；
- 设备模型、建模命令和求解算法具备开发、安装、选择、替换和版本比较流程；
- 可调负荷和市场场景完成输入、优化、结果和报告闭环；
- 问答、Excel 标准化、报告生成和 Open WebUI 均有可撤销、可确认和可审计语义；
- 可选数据 Provider 具备白名单、数据版本、降级和溯源。

### 正确性门禁

- 每种新增设备有合成案例和代表性工程案例；
- 每个关键指标有参考结果和容差；
- 典型工况能保留极端边界，且典型时段与全年校核偏差满足门限；
- 两个算法 Provider 的对比使用同一不可变输入和一致状态语义；
- 多分辨率和不确定性分析结果语义一致；
- 历史结果快照追踪测试通过；
- AI 报告关键数字与证据包自动交叉校验通过。

### 安全门禁

- 凭证不出现在日志、项目包和普通导出；
- 可选外部请求只能访问白名单数据/AI Provider；
- 插件不能访问其他模块内部、任意数据库连接、任意对象路径或用户会话；
- AI 上下文经过权限和脱敏过滤；
- 用户确认前不会写入权威版本；
- 外部服务故障和超时不会造成任务无限等待。

### 运维门禁

- Docker 部署、迁移、升级、回滚和恢复均有固定操作入口；
- 插件安装、升级、禁用、替换和回滚均在 Docker 流程中完成；
- 计算队列与 I/O 队列具有资源隔离；
- 插件 Registry、可选数据 Provider 和 AI Provider 的健康状态可观测；
- 缓存、原始响应、转换对象和报告版本可清理但不误删被引用对象；
- 版本 1 项目可以在版本 2 中读取、查看和重新计算。

# 13. 风险与控制措施

| 风险 | 影响 | 控制措施 |
| --- | --- | --- |
| 新设备只完成 UI，未完成能流和规划约束 | 结果不可用 | 每种设备必须以垂直切片交付，并包含合成案例、求解、财务和导出 |
| 典型工况丢失极端边界 | 容量偏小或全年运行不可行 | 极端时段强制保留、全年校核、偏差门禁和自适应重算 |
| 插件契约过于宽泛或形成全局 Registry | 模块耦合、历史任务不可复现 | `devices`/`modeling` 独立 Registry、公开契约、一次性发布和快照固定版本 |
| 插件升级或替换改变历史结果 | 审计与重现失效 | 新修订/新快照语义、历史版本保留、同输入差异报告 |
| 元启发式算法被宣称为已证明最优 | 用户对规划结果产生错误信心 | 算法能力声明、基准案例、统一停止状态、Gap/边界证据和显著的未证明最优标记 |
| 可选外部数据 Provider 响应不稳定 | 数据不可复现 | Provider 版本、原始对象、内容 hash、转换版本和离线降级 |
| 外部数据覆盖用户权威数据 | 历史结果被污染 | 外部响应先生成独立引用版本，用户确认后才能绑定快照 |
| AI 生成错误参数或结论 | 工程和财务误判 | 结构化 schema、置信度、用户确认、结果证据交叉校验 |
| 可选外部数据/AI Provider 凭证泄露 | 安全和合规风险 | 密钥存储、脱敏日志、权限隔离、导出排除和轮换 |
| 本地 Open WebUI 接口不兼容 | AI 功能不可用 | Provider 能力发现、最小兼容协议、规则引擎和非 AI 降级 |
| 二期设备扩大求解规模 | 任务超时和资源耗尽 | 规划规模基准、设备组合白名单、任务资源额度和超时状态 |
| 版本 1 结果与二期模型不兼容 | 历史证据不可读 | schema 版本、迁移规则、旧项目只读兼容和重新计算提示 |
| AI 报告掩盖失败状态 | 错误决策 | 报告模板强制展示业务结局、适用范围、失败原因和未证明最优状态 |

# 14. 最终建议

二期最合理的交付路径不是“先做 AI，再补模型”，而是：

1. 先修复版本 1 的快照、结果、任务和部署基础问题；
2. 将计算规格中的典型工况、完整容量 MILP、全年运行校核、偏差重算和真实 Pareto 闭环实现到产品；
3. 建立 `devices` 设备 Registry 与 `modeling` 建模命令/算法 Registry，完善公开契约、插件 SDK 和替换流程；
4. 逐类以插件形式实现新增设备和柔性资源，并建立可验证的计算闭环；
5. 建立用于规划仿真的历史/预测电价和源荷偏差场景，但不进入实时交易或运行控制；
6. 在结构化插件能力和数据契约稳定后，交付问答式信息收集与候选模型/算法推荐；
7. 在标准化数据稳定后交付 AI Excel 标准化；
8. 在结果证据、运行校核、敏感性和质量状态稳定后交付可解释 AI 报告；
9. 最后接入本地 Open WebUI，作为统一 AI Provider 的部署选项；
10. 通过端到端、插件替换、离线、迁移、权限和恢复验收后再发布二期。

其中，**模型与算法插件化是二期的早期基础能力**：它决定新设备、新建模方法和新求解算法能否在不破坏模块边界和历史可复现性的前提下开发与替换。外部 API 只作为可选数据或 AI Provider 的一种实现方式，不再主导 roadmap，也不得成为核心计算或历史结果读取的必需条件。
