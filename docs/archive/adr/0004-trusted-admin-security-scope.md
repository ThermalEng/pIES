# ADR-0004：集中部署信任模型与安全审计范围

> 状态：已批准、文档已实施、已归档  
> 决策日期：2026-08-22  
> 批准依据：项目所有者明确同意  
> 修订条款：架构宪法第 16 节；领域模型“身份、权限和审计”

## 问题

pIES 的部署场景是管理员集中部署，普通使用者通过界面和 API 使用。管理员的配置、恢复和维护行为属于受信任运维行为，权限区分主要用于防止误操作和普通使用者越权，而不是为了建立管理员之间的对抗性隔离。

原有“所有管理操作必须审计”的表述范围过宽，容易把日常查看和普通维护解释成重型安全审计要求，也没有明确系统的管理员信任模型。

## 决策

1. 将管理员视为受信任运维角色，不把管理员主动修改本身作为攻击事件，不要求管理员相互隔离、双人审批或零信任架构。
2. 安全边界重点防护未登录请求、外部请求、普通使用者越权和不可信输入，继续保留认证、项目范围授权、上传/下载边界、敏感信息保护、禁止任意代码执行、SolverRuntime 命令 allowlist、路径/网络/资源限制和进程回收要求。
3. 审计范围收窄为权限、所有权、对象清理、项目/数据/计算配置、恢复和人工评估等关键变更；审计记录仍不可变、最小化并脱敏，普通查看和日常运维不要求重型审计。

## 影响

- Roadmap 的安全复审以第三方攻击面和误操作防护为门槛，不再把管理员相互隔离或额外审批列为发布条件。
- 管理员仍能直接完成部署、配置、恢复和维护；危险操作通过作用范围提示、确认和版本恢复降低误操作风险。
- 对外请求、普通使用者访问范围和恶意文件/参数的防护不变，计算执行边界仍保持受控。

## 被否决方案

- 把管理员当作与外部攻击者相同的威胁主体：与集中部署模型不符，会引入不必要的管理复杂度。
- 为管理员增加双人审批、相互隔离或全量操作留痕：不能显著提升本产品场景下的第三方攻击防护，且会阻碍日常运维。
- 删除普通使用者项目范围授权、上传限制或 SolverRuntime 隔离：会削弱真实的第三方输入和越权防护。

## 迁移与回滚

本次只修改架构宪法、领域模型和 Roadmap 对应的规范文字，不要求代码迁移。若部署模式或威胁模型发生变化，应重新提交 ADR，评估是否恢复更严格的管理员隔离或审计要求。
