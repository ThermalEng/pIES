## 为什么做、完成后得到什么

验证设备声明是可替换的真实扩展内容，而不是必须修改核心代码或 GUI 才可消费的内置特例。完成后应有可复跑的外部 YAML 样例、隔离部署覆盖与浏览器证据，证明全新稳定 ID 能被发现、选择、拖放连接、装配提交并通过通用执行链产生真实结果；错误候选不能发布部分目录。

## 裁决及提交边界

1. 注入使用隔离 Compose 覆盖，只读挂载到现有扫描目录的新子目录。不修改生产 Compose 或遮蔽内置内容，不新建外部目录配置对象、注册框架或热加载入口。
2. 重复稳定 ID 的静默覆盖是真实缺陷。先用独立小提交在设备候选集合入口拒绝跨文件 ID 冲突，沿用现有配置诊断和原子发布逻辑；Docker 定向证明修正前失败、修正后拒绝冲突且失败不替换已有有效集合。不是摘要/hash/内容去重，不在每次读取或消费者中重复检查。不顺带重写 loader、schema 或清理无关防御代码。
3. 第二笔提交交付一条外部设备公开消费链：选择器→真实画布拖放/连线/参数→草稿及装配→任务提交→真实 Worker 求解→完成结果。其他配置可复用既有公开 API 脚手架；不得替代被测的设备选择与画布动作，不能注入页面状态、mock 求解或预写结果。导出流程此前已验收，本切片不要求重复完整导出测试。
4. 外部 YAML、覆盖文件和定向验收脚本可作为测试工件入库，不写入内置 catalog。运行时从独立内容目录只读挂载，不依赖核心代码中的设备 ID 分支；仓库保存可复跑样例不等于将其内置注册。
5. 非法 YAML 和重复 ID 的拒收用定向 Docker/公开初始化入口验证即可，无需为每个负例重建整套 GUI 栈。使用公开观察结果证明原子性，不读取或修补私有注册表状态来凑通过。
