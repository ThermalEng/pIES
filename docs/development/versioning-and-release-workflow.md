# 内部版本化与发布流程

> 文档类型：内部过程控制；状态：生效；产品版本、已完成事项与后续计划以 `manual/changelog/` 为准。
>
> 本文不定义产品架构、公开文件契约或用户行为；这些内容以 `manual/` 的对应正式章节为准。

## 三段式版本

产品版本统一为 `MAJOR.MINOR.PATCH`：

- `MAJOR`：对架构或公开契约进行不兼容重构；
- `MINOR`：向后兼容地增加新功能；
- `PATCH`：向后兼容地修复缺陷。

正式标签使用 `vMAJOR.MINOR.PATCH`。文档、界面、API、快照和导出包中的产品版本都必须是完整三段式，不使用 `1.0`、`版本 1` 或“二期”代替程序版本。

内部重构若不改变公开行为，不单独提升主版本；它随实际用户影响进入 minor 或 patch。schema、项目包格式、provider 和文档修订拥有独立版本，不与产品版本机械同步。

## `0.x` 阶段

`0.x` 表示正式发布前，公开契约仍可能收敛：

- 正式产品版本、已完成开发里程碑和下一目标只读取 `manual/changelog/`，不在本文重复维护；
- 新功能通常提升 MINOR，例如 `0.2.0`；
- 缺陷修复提升 PATCH，例如 `0.1.1`；
- 正式发布前的不兼容整理也通过新的 `0.MINOR.0` 交付，并在更新日志明确迁移影响；
- 完成发布门禁后统一进入 `1.0.0`。

`1.0.0` 之后，不兼容架构或公共契约重构才进入 `2.0.0`。

## 版本权威源

Python 项目元数据 `backend/pyproject.toml` 是产品版本唯一权威源。后端运行时从已安装包元数据读取版本；前端帮助清单在构建时读取同一来源。

`frontend/package.json` 只描述私有前端构建包，不作为产品版本。统一设备 schema、算法插件/provider 和测试工具各自的 contract/语义版本也不等同于产品版本；单个设备只以内容摘要和发布 revision 固定，不拥有独立语义版本。

## 更新日志

[更新日志](../../manual/changelog/README.md)按新版本在上的顺序维护：

1. `Unreleased` 收集已经实现并通过相应验收、但尚未发布的用户可感知变化；
2. 未正式发布但已经完成的开发里程碑，在 `Unreleased` 内按目标版本分别归档，不把多个版本混成主题清单；
3. 每个版本条目必须明确写出完成日期、版本进展、更新内容、解决的问题和迁移/兼容影响；
4. 发布时把对应里程碑从 `Unreleased` 转为正式版本号和发布日期；
5. 只记录外部行为、公共设计和迁移影响，不写文件行号或实施流水账；
6. 未来计划只写入[Roadmap](../../manual/changelog/roadmap.md)；
7. 实现一项 Roadmap 工作时，同一次变更把完成事实写入 `Unreleased` 并从 Roadmap 删除；部分完成只迁移已完成子项。

Roadmap 不是历史记录或状态看板，不保留完成勾选、删除线、完成日期和“已完成”小节。某个目标版本没有剩余工作时，从 Roadmap 删除整个版本段落；版本历史由本页保存。

## 发布门禁

发布候选至少满足：

- 版本号、Git 标签、API、帮助中心、快照和导出元数据一致；
- 更新日志已从 `Unreleased` 整理为目标版本；
- 使用者指南与实际 GUI 一致，未实现能力仅在 Roadmap；
- 数据和公共契约迁移说明完整；
- 安全发布阻断已复核关闭；
- Docker 内后端、前端、迁移和系统测试通过；
- 画布拖放完成人工核查；
- 镜像带有版本与修订标识，可回滚到上一发布；
- 备份和恢复演练通过。

尚未完成的发布准备工作见[Roadmap](../../manual/changelog/roadmap.md)。

## 一次版本开发怎样开始

1. 从 Roadmap 选择一个目标版本和退出标准；
2. 把目标拆成可独立验收的用户能力或公共 contract；
3. 为每项变化判断 MAJOR、MINOR 或 PATCH 影响；
4. 按模块手册完成实现、迁移、测试和文档；
5. 单项通过验收后，把完成事实写入 `Unreleased` 并从 Roadmap 删除；
6. 部分完成时只迁移已完成子项，继续保留清晰的剩余工作；
7. 目标版本的 Roadmap 段落清空且全部退出标准满足后，才进入发布候选。

版本号不是开发阶段名称。一个目标未完成时不能通过提前提升版本号宣称完成；已经实现的变化不能继续留在 Roadmap，已经发布的变化也不能留在 `Unreleased` 不归档。

## 发布操作顺序

```text
冻结范围与公开 contract
  ↓
完成迁移、文档、安全和测试门禁
  ↓
把 Unreleased 整理为目标版本 + 日期
  ↓
更新唯一版本源
  ↓
构建全新镜像并核对 API/帮助/快照/导出版本
  ↓
执行升级、备份恢复和回滚演练
  ↓
创建 vMAJOR.MINOR.PATCH 标签并发布
```

若镜像构建后发现版本不一致，应修正唯一版本传播链并重新构建，不能手工修改某个页面或导出文件中的显示值。

## 发布后修复

已发布版本出现缺陷时，先判断修复是否保持公开兼容。兼容修复进入 PATCH；需要新增用户能力进入 MINOR；必须破坏 contract 才能修复时进入 MAJOR，并提供迁移。修复应在更新日志说明受影响范围、迁移要求和是否需要重新计算历史结果。
