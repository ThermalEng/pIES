## 2. 唯一真实缺口（不猜列名、不硬编码设备 ID，不以旧字段宇宙为目标）

- `solution.variables` 里有全步数值与单位，但**没有稳定声明**给出：
  序列身份（公开装配实例 + 接口/已声明变量身份）、具体求解列引用（每个 step 对应的 LP 列）、
  步数与业务单位。`{inst}__{local}__t{step}` 只是生成器内部确定性命名
  （`modules/generators.md:77` 只说“实例与时步确定命名”，未把格式立为跨边界稳定契约），
  任何按名反解（如下游再拼 `__t{n}` 或按设备 ID 硬编码列）都违反宪法禁令。
- 旧字段名（`p_grid_buy`/`pv`/`soc` 等）只是现 GUI 遗留消费集合与零散工程词汇
  （`metrics/engineering.py:67`），**不作为新契约目标**：新契约的序列身份只取公开装配
  实例 + 接口/已声明变量身份并带真实单位，前端改按公开元数据通用选取/展示，
  不按设备类型或旧名称猜语义，不新增另一套类型注册表或泛化框架。
- 归属错误纠正：序列恢复的拥有者是 **ResultAdapter**（解释求解输出），不是 application；
  application 只拥有已恢复统一序列的对象序列化/存储/引用/DB 事务封存，
  绝不解释 Bundle 变量或按名称拆 step；Worker 只编排。
  现行唯一真实适配器为 `HighsResultAdapter`（`computation/__init__.py:31`“首个真实结果适配器”），
  它只发布 solution/metrics；仓库内无第二种生产 provider，结论来自代码而非单任务反推。

可复用的现有权威（不需新造）：`unit_map`（LP 名→单位）、`solution.variables`、
财务分量声明先例（`finance_component_declarations` 由配套 Adapter 用同一次真实解求值发布，
`project.py:240-254`）、`read_hourly` DTO 与 `results/rules.py` 的字段/rows 结构校验、
快照时域（`horizon_point_count`，`project.py:221-228`）、`CalculationConfig.outputs` 门控、
候选/选择既有身份（S3-A，不为序列新造身份；多解归属沿用 `solution_id` 与 receipt/bundle 追溯）。

## 3. 最小契约修订草案（唯一草案，呈 Codex 修订，本轮不实施）

先例：财务分量 `components` 声明随 `parameters.json` 发布、配套 Adapter 用同一次真实解求值，
不重建模型（`project.py:240-254`，`highs.py:212-266,405-434`）。步序列沿同一模式：

1. **Generator 声明**（computation 拥有，随 Bundle `input/parameters.json` 发布，
   与 `unit_map` 同一构造器、同一输入恒得同一声明）：`step_series` 条目每条含
   - 序列身份：装配实例 + 接口/已声明变量身份（如 `instance: "hp1"`，
     `interface: "electricity_in"`），不含旧字段名；
   - 具体求解引用：按 step 顺序的显式 LP 列名表
    （如 `columns: ["hp1__electricity_in__t0", …, "hp1__electricity_in__t8759"]`），
     不给命名规则让下游重构；
   - 步数（`steps`，与时域点数一致）与业务单位（`unit`，与 `unit_map` 同源）。
2. **ResultAdapter 恢复发布**：消费该声明 + 同一次求解输出（经 MPS 列序取 primal，
   与 variables 同一路径），反向换算到业务单位，发布到
   `ComputeResult.outputs.series = {series_id: {instance, interface, unit, values}}`；
   残缺即沿现有 `_fail` 语义自然失败，不补零、不回退旧解析。
   与输出请求的关系：series 随 `solution` 请求发布（同一组 primals 与换算）；
   `metrics-only`（未请求 solution）无 series，诚实缺席；**不动封闭的
   `CalculationConfig` 输入**，不新增输出请求词汇。
3. **application 封存**：只消费已恢复的统一序列（`outputs.series`），序列化 hourly 对象
   `{data, meta.units}` 经 storage 落盘，在提交同一事务内封存
   `{object_id, fields, rows}` 引用（`fields` 取序列身份，`rows` 取实际长度）；
   不解释 Bundle 变量，不按名称拆 step，不做长度比对/hash/完整性复核。
   **Worker 只编排调用**，不拼业务序列。
4. **版本**：`ComputeResult.outputs` 是显式可扩展容器
   （“具体业务候选字段由后续适配实现按声明输出填充”，`protocols.py:1015-1030`），
   且 `_parameters` 对未知键忽略（`highs.py:212-266` 只要求既有键），
   故新增 `step_series`/`outputs.series` 不需要形状版本变更：
   `COMPUTE_RESULT_VERSION` 保持 `"2.0.0"`、`CALCULATION_CONFIG_VERSION` 保持 `"1.0.0"`，
   无声默改动；若 Codex 认定声明本身需版本化，请以 generator 版本为准另立，不编新号。
5. **应进入的 manual 唯一正文**（实现前由 Codex 修订，暂不写）：
   - Generator/Adapter 公开声明形状 → `modules/generators.md`、
     `modules/solver-runtime.md`（适配节）、`formats/solver-bundle.md`
    （`parameters.json` 的 `step_series` 形状）；
   - `ComputeResult.outputs.series` → `modules/engines.md`（结果适配节）；
   - hourly 引用与 `/hourly` 元数据（字段身份/单位/归属）→ `contracts.md`
    （时间/逐时查询契约节）；
   - 步时域推导 → 已有 `core` 时域权威，不新增；候选身份 → 已有 S3-A 权威，不新增。
6. **明确不做**：不把输入物化序列冒充求解输出；不重新求解；无 hash；
   无内部重复校验/补零/备用旧解析（无声明的老 Bundle 沿现行语义直接失败）；
   不改宪法。
