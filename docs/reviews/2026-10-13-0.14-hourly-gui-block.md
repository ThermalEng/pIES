## 2. 唯一真实缺口（不猜列名、不硬编码设备 ID）

- `solution.variables` 里有全步数值与单位，但**没有稳定声明**把
  `{inst}__{iface}__t{step}` 映射到 hourly 字段名（如 `p_grid_buy`）：
  该命名是生成器内部确定性命名（`modules/generators.md:77` 只说“实例与时步确定命名”，
  未把 `__t{step}` 格式立为跨边界稳定契约），按名反解违反宪法“不得按名称猜测”禁令。
- **没有所有者**把 `ComputeResult.solution` 建成 hourly 对象
  （`{data:{field:[...]},meta:{units}}`）并经 storage 建对象、application 在同一事务封存引用。
  现行唯一真实适配器为 `HighsResultAdapter`（`computation/__init__.py:31`“首个真实结果适配器”），
  它只发布 solution/metrics；仓库内无第二种生产 provider，结论来自代码而非单任务反推。

可复用的现有权威（不需新造）：`unit_map`（LP 名→单位）、`solution.variables`、
`read_hourly` DTO 与 `results/rules.py` 的字段/rows 结构校验、快照时域
（`horizon_point_count(baseline.resolution, start_year, operation_years)`，
`project.py:221-228`）、`CalculationConfig.outputs` 门控。

## 3. 最小闭环建议（呈 Codex 裁决，本轮不实施）

1. 由 **Generator（computation 拥有）**在 Bundle `parameters` 中随 `unit_map` 附带一份
   稳定的步序列描述子：`[{field, inst, iface, unit}]`（字段名由生成器按装配绑定声明，
   不是前端猜、不是 Worker 拼）。
2. 由 **application（results/worker 应用层拥有）**在提交同一事务内消费
   `ComputeResult.solution` + 该描述子，建成 hourly 对象经 storage 落盘并封存
   `{object_id, fields, rows}` 引用；**Worker 仅编排调用**，不得解析求解器变量名或拼业务序列。
3. `metrics-only`（未请求 solution）继续诚实缺席，不伪造空序列；GUI 缺席态留 R3。
4. 若上述描述子被认定为新稳定结果契约，按宪法先立规范再实现；不改 `ComputeResult` schema，
   不把输入物化序列冒充求解输出，不新增整层抽象。
