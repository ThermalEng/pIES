# `0.13.0` 退出审计（只读盘点）

- 日期：2026-10-12；基线：master `68602a9`（已含 `7b59703` → `3ad55da`）。
- 范围：Roadmap `0.13.0` 退出标准——用户可在 GUI 中完成“创建版本 → 应用方案 → 查看历史结果 → 恢复/导入”，且新旧版本和审计记录可见。
- 方法：只读源码检查＋复用已有 Docker 验收证据，未重跑全仓测试，未新增实现。本轮三路并行检查（版本/恢复、应用/历史、审计记录/文档一致性）， decisive 断言已由本报告作者二次 grep 复核。
- 本报告不是新规范；真实缺口只报告不停下实施（除本报告文件的独立提交外）。

## 1. 创建版本 GUI — 已满足

- 入口：工作台侧边“版本历史”，路由 `/projects/:id/versions`（`frontend/src/pages/ProjectPage.tsx:36`、`WorkbenchPage.tsx:97`）。`VersionsPage` 只组合 feature。
- 身份展示：列表 `v{no}/name/created_at/reason`（`VersionHistoryPanel.tsx:299-323`）；详情 `v{no}/name/description/reason/来源草稿修订/基线/创建人行`（`:128-153`）。创建失败保留输入并展示后端错误；只读失败走 `Alert(load_failed)`，仅成功空数组才显示“尚无版本”（`:281-296`，hook 失败保持 `versions=null`）。
- 权限：前端无预检；归档项目创建由后端 `ConflictError` 拒收并透传展示（`application/projects/versions.py:185-191`）。
- 证据：Docker Playwright `project-versions.spec.ts` 3 通过（两版本创建与持久、迟到详情隔离、归档拒收；被测创建/选择经 GUI，脚手架走公开 API）。

## 2. 应用方案 GUI — 已满足

- 候选来自 `res?.candidates` 按 `index` 排序，不按指标键反解（`ResultsPage.tsx:199,356-357,487-491`）。`pickMetrics/findMetric` 正则（`:117-131,465-485`）仅用于指标分组展示，候选与规划解不经过它们。
- 参数预览渲染冻结 `variable + device_ref + parameter + 值单位` 及解引用（`:1045-1063`，确认框内 `:1288-1302`）；服务端投影为“封存解 × 同一快照冻结绑定”（`results/rules.py:105-131`，`versions.py:481-502`）。
- “选择”与“应用”文案区分（选择仅标记采用，`messages_zh.ts:610-611`；应用写入并派生版本，`:615-616`）。但 `zh:611` 与 `en:601` 选择确认文案仍含“实际应用方案尚未交付”，与已交付的应用方案矛盾，属文字偏差（见 §7）。
- revision 冲突：开框现读 `draft.revision` 作确认基线展示，POST 固定发捕获的 `expected_revision`，发送前不重读（`:548-600`）；后端不符 409，前端框内展示（`versions.py:530-544`）。取消零 POST；写飞行中禁用证据选择/关闭/取消；成功后必刷新且成功与刷新失败分开报告。
- 证据：`result-apply-scheme.spec.ts`（取消零 POST、确认恰 1 POST、v3 派生与内容复核、刷新失败分支）、`result-apply-scheme-guards.spec.ts`（C1 确认后修订 409、C2 写飞行隔离与 POST 失败/修订读失败分支）Docker 通过。

## 3. 查看历史结果 — 已满足

- 来源标签仅由快照引用驱动：版本按 `project_version_id` 精确匹配，数据集按冻结 `dataset_version_ids` 逐库查版本，未命中显示精确 `id`，不造名（`ResultsPage.tsx:389-435,750-763`）。确调用当前 `api.datasets.list` 作名字索引，但选择键始终是冻结 id，枚举全部版本而非取最新，无混用。
- 证据：`result-planning-solution.spec.ts`（计算后新增数据版本/草稿改动不改变历史显示，重登 GUI 仍 v2 + 样本 v1）、`result-switch-failure.spec.ts`（迟到结果不覆盖）Docker 通过。

## 4. 恢复 GUI — 已满足

- 证据：`project-restore.spec.ts` T1–T4 Docker 通过（恢复 v1 建 v3 及内容复核、重复提交单 POST、当前版本恢复撤回未固化改动、摘要刷新失败分离）。

## 5. 导入 GUI — 已满足

- 项目列表“导入项目包”：上传→服务端提案（名/币种/暂存对象数）→明确确认才建独立新项目；确认前 `project_id=null`，不导航不预建；`reasons` 逐项；确认失败同一提案重试；取消仅关本地界面（无取消 API，未新增）；忙碌禁用文件更换与关闭；迟到响应序号丢弃；`done.refresh` 区分导入成功与列表刷新（`features/project-import/`，`ProjectsPage.tsx`）。

## 7. 审计记录可见 — 真实缺口（0.13 退出未达成项）

- 后端确有写入：版本创建/快照固化（`versions.py:215-230,274-314`）、方案应用（`:632-664`，`version_created` reason=`apply_result` ＋ `project.result_applied` 同一事务，唯一 `db.commit()` 在 `:665`）、恢复（`:442-470`）、导入提案与确认（`packages/transfers.py:966-973,1002-1074,1408-1423`）、结果查看选择（`results/writes.py:268-282,448-459,553-564,621-636`）。
- 但 GUI 零入口：`frontend/src/pages/` 与 `features/` 内零 `audit` 引用（复核 grep 空）；`GET /admin/audit` 后端存在（`api/admin.py:47-62`），`api.admin.audit()` 客户端存在（`client.ts:1939-1947`），无任何页面调用；管理页仅账号管理（`AdminUsersPage` 无审计引用）；版本页/详情/恢复完成态均不展示审计行。DB 有记录 ≠ GUI 可见。
- 最小缺口：对上述已写入审计行的只读查看入口（按现有契约与实际页面判定范围）；不扩展成审计管理平台，不新增写能力。待 Codex 裁决后再实施。
