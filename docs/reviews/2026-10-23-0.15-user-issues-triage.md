## 1. 总体结论与证据边界

当前主要障碍是：工程用户无法仅靠界面完整表达规划问题及其经济关系；另有已经批准、尚需补齐的计费和维护能力。不能把后端 API 已存在、开发测试已通过或预检没有阻断当作用户已经能够完成工作。

证据分层：

- 主审已核实：缺少规划配置及实例财务／计费绑定的前端入口；规划引用为任务提交的实际必需输入。
- 正式规范已经明确：月最大需量计费、年度维护清单的规模／成本关联语义。具体实现缺口需在派工前定位，不能仅凭页面没有字段推断全部后端均不存在。
- 现行格式已明确但使用不便：价格序列要求覆盖运营全期；周期输入是待设计的能力增补，不能说现有实现违反该格式。
- 模拟用户报告、尚需复现或完善说明：出力型模型易用性、核算边界表达、画布遮挡／连线操作困难。

模拟用户早期报告存在跳过必要操作后记录成功的问题。旧的“完整通过”结论已撤回；新问题也逐项判断，不因报告已列出就一律认定为程序缺陷。

核实依据：[架构宪法](../../manual/developer-guide/zh-CN/ARCHITECTURE_CONSTITUTION.md)、[装配格式](../../manual/developer-guide/zh-CN/formats/assembly-yaml.md)、[财务格式](../../manual/developer-guide/zh-CN/formats/finance-yaml.md)、[财务模块](../../manual/developer-guide/zh-CN/modules/finance.md)。规划入口及冻结引用的代码证据位于本基线的 `frontend/src/pages/ConfigPage.tsx`、`backend/iesplan/api/config_revisions.py`、`backend/iesplan/application/tasks/submissions.py`；前端没有规划配置、实例财务绑定或计费绑定的业务请求入口。

### A. 规划配置入口（ISSUE-05）

- 事实：后端有规划配置公开保存接口；前端工作台没有相应编辑保存流程。任务提交实际读取冻结的规划引用，缺失时拒绝。首次建项同样受影响，不仅是财务配置变更后。
- 预期：用户能在界面表达目标、变量与边界／约束，保存、重新打开并用于提交。财务变更导致失效时，有可到达的重新确认和保存路径。
- 完成证据：从普通新项目通过界面建立规划配置并完成任务创建；修改后读取与冻结值一致。
- 不采用：删除必需输入检查、自动编造规划目标、API 预置规划后声称 GUI 已闭环。

### B. 实例成本与计费绑定入口（ISSUE-03）

- 事实：装配已有显式实例财务绑定和计费绑定规则、后端草稿命令；前端没有对应的用户编辑入口。
- 预期：用户能指定实例是否参与成本核算、采用的成本模型及驱动量，并指定计费对象、计量接口与已有价格的关系；允许明确无计费，不猜关联。
- 完成证据：界面保存、重开、任务冻结与项目包往返保持相同关系；改变计量对象后结果反映该关系。
- 不采用：按设备名称／类型自动猜财务归属；把成本塞进纯技术模型；保留只能由开发脚本写入的必需事实。

### C. 画布操作可靠性（ISSUE-08）

- 当前证据支持继续调查，但不足以认定所有连线失败都是产品缺陷。此前也有真实鼠标拖放、连线成功的 Docker 浏览器证据，不能把“普通鼠标无法触发 HTML5 拖放”当作已证实根因。
- 先区分定位器／等待错误、保存冲突、节点遮挡、端口命中等实际原因，记录具体视口、缩放、操作和保存后的节点／连接事实。
- 完成证据：普通界面操作可稳定放置、选中、编辑和连线；未成功时有可理解反馈。是否增加点击连接或列表连接，依据复现结果决定，不先指定两套新交互。

### D. 周期价格输入（ISSUE-01）

- 事实：现行财务价格格式要求覆盖运营全期。用户不便自行生成全期文件，是产品输入能力不足，不是现有校验错误。
- 预期：用户可显式表达原样全期价格或周期价格及其适用规则，形成确定的全期输入；已有年度差异能够保留，不能统一循环覆盖。
- 派工前：由主审先明确周期循环与公历对齐的关系、月份／闰日处理及公共载体；不在本清单中擅定字段或默认复制规则。
- 完成证据：不同起始年和跨年边界的价格取值正确；用户无需编写程序展开数据；历史任务不读取当前可变规则。

### E. 月最大需量计费（ISSUE-04）

- 上游依据：财务模块手册“月最大需量计费”已经明确通用要求。
- 预期：用户明确计量点、费率和金额口径，各自然月分别取峰并计费；费用参与同一次优化，并按年进入同次解现金流与报告。
- 完成证据：用各月峰值不同的合成输入核对月费与年费，并证明改变调度／规模可影响这项成本。
- 不采用：以全年峰值代替月峰值；把功率上限当作需量收费；求解后附加账单却不参与优化。

### F. 规模关联年度维护（ISSUE-06）

- 上游依据：财务模块手册已经要求年度维护清单支持确定金额、单位费用乘实例规模变量、实例成本分量乘比例及其组合。
- 预期：同一维护清单显式给出发生年和金额来源，随本次选建规模确定金额；优化、税务、现金流与导出使用同次解。
- 派工前：盘点现有公开维护清单及税务逐项引用，主审补齐最小字段契约，不让实现者自行发明表达式语言。
- 不采用：预先固定候选规模；求解后才扣费；内置某设备的更换年份、周期或比例；删除按实际运行量归集的可变运维。

### G. 出力型模型易用性（ISSUE-02）

- 需求：用户已有单位装机出力序列时，可用明确的模型／模板绑定该序列与规模，不必先取得气象数据或手写技术方程。
- 建议：先使用现有声明式设备模型与模板能力补齐通用模型内容及入口说明，保留气象驱动模型。
- 完成证据：普通用户能选择适当模型，正确理解序列与容量的单位关系，并从页面完成输入；调整规模后出力及物理约束相应变化。
- 不采用：按客户、文件名或设备 ID 在解析器／生成器中特判；未经需要提前建设模型库、插件热加载等后续系统。

### H. 核算边界可理解性（ISSUE-07）

- 当前是“用户无法确认怎样核算”，不是“已证明重复收费”。
- 预期：用户能从已有财务模型与计量绑定看清哪些是外部收入／支出、哪些是内部能量转移；需要比较时明确基准与增量关系。输出能解释损耗如何体现、费用如何归集。
- 不预设“投资方／厂区”硬编码开关，也不新建独立财务计算引擎。先检验现有通用配置能否表达，并完善入口与说明。
- 完成证据：同一物理系统采用不同、明确的经济边界时，可得到可解释的核算；不重复计算同笔交易、能量损耗或维护支出。

## 3. 暂不列为已发现缺陷的后续检查

- 系统评估、指定任务报告导出及与页面结果的一致性。

入口打通后再由模拟用户继续使用、发现问题。没有运行或没有证据的部分保留“未验证”，不写成通过或程序缺陷。
