# 0.14 预出口审查报告

- **日期**：2026-10-16
- **审查对象**：0.14 收尾前代码整体审查
- **提交基线**：1f57e19（docs: record model loading lifecycle acceptance）
- **审查范围**：backend/iesplan/ 全模块 + frontend/src/ 全体
- **审查目的**：识别阻断 0.14 退出或需在 0.15 前修复的问题

---

## 总体结论

架构边界整体守住：核心模块依赖方向正确，跨模块 import 通过 application 层中转，没有发现 api 层直接查询 ORM 或领域模块反向依赖上层的情况。发现的问题主要集中在以下几个方向：

1. **前端模块级状态缓存**（高）：`client.ts` 有三个模块级 Map 缓存，违反宪法 0.14 退出目标"删除模块级业务缓存"
2. **前端 admin.storage() 字段 bug**（高）：`used_bytes` 错误赋值为 `total_bytes`
3. **assembly 中的宽泛 except**（中）：部分业务函数用 `except Exception` 掩盖了具体失败类型，可能静默错误
4. **imports 中的 integrity 字段**（中）：`transfers.py` 在导入提案 review_summary 中写入 `integrity_ok: True`，属于内部流程冗余完整性标记，违反宪法 §2.6
5. **前端 validation.baselineConfirm 丢弃诊断**（中）：后端返回 diagnostics 但前端硬编码返回空数组
6. **前端 client.ts 超大单文件**（低）：2186 行，所有 API 方法、适配辅助、缓存全在一个文件，难以维护

## 一、高严重性问题

### H-01 前端模块级 Map 缓存违反 0.14 退出标准

**文件**：`frontend/src/api/client.ts:937–993`

```ts
const pkgTaskCache = new Map<number, number>()       // 证据包 → 任务 id
const resultBodyCache = new Map<string, Record<string, unknown>>()  // 结果体缓存
const downloadSessions = new Map<number, {...}>()   // 下载会话
```

**问题**：

- `pkgTaskCache`：在 `tasks.get()` 中写入，在 `resolveAssessmentId()` 中读取，用于 `exports.excel()`。若刷新页面或换任务，缓存失效但 Map 仍有旧值，导致 Excel 导出可能使用错误的 `assessmentId`，静默拿旧任务的评估。
- `resultBodyCache`：`results.result()` 写入，`results.hourly()` 读取。缓存不设 TTL、不随任务状态变化失效。若同一 `projectId:taskId` 任务重试后有新结果，hourly 仍读旧体。
- `downloadSessions`：生命周期管理缺失，页面不刷新时 Map 持续增长。

**宪法依据**：§9 "删除模块级业务缓存"；0.14 退出标准"无兼容猜测"。

**修复建议**：
- `pkgTaskCache`：`exports.excel()` 收到 `pkgId` 后直接在调用链内查 taskId，不用模块全局缓存；或在 `tasks.get()` 后立即传递 taskId 给调用方，不中继缓存。
- `resultBodyCache`：在 `results.hourly()` 入参中直接接受 taskId，与 `results.result()` 合并为一次请求，或完全移除缓存让调用方自行去重。
- `downloadSessions`：改为 React state/context，绑定页面生命周期，离开导出页自动清除。

### H-02 admin.storage() used_bytes 错误赋值

**文件**：`frontend/src/api/client.ts:1987–1988`

```ts
total_bytes: Number(objects.total_bytes ?? 0),
used_bytes: Number(objects.total_bytes ?? 0),  // BUG: 应是 used_bytes
```

`used_bytes` 和 `total_bytes` 被赋为同一个值。管理员存储视图会显示"使用量 = 总量"，永远看不到剩余空间。后端 `objects` 对象中是否有独立的 `used_bytes` 字段需核实，若无则需对齐后端响应契约。

## 二、中严重性问题

### M-01 assembly 中的宽泛 except 可能掩盖错误

**文件**：多处

```python
# assembly/context.py:278
try:
    units.convert(1.0, a, b)
    return True
except Exception:   # 吞掉了所有异常，包括内部 bug
    pass

# assembly/context.py:321 - to_watts()
try:
    return units.convert(float(value), unit or "W", "W")
except Exception:
    return None   # 单位不合法 → None，但内部 bug 也变 None
```

`to_watts()` 返回 `None` 会在调用方静默处理，实际上单位换算内部报错和"单位确实不可换算"被混同处理，违反宪法 §2.5 "失败可见"。应改为仅捕获 `UnitConversionError`（或等价的业务异常），其余异常上浮。

**文件**：`assembly/rules/planning.py:203`

```python
try:
    symbol = str(exc.params.get("variable", ""))
except Exception:
    symbol = ""
```

这是"取参数的参数"中套的异常捕获，合理但过于防御。`exc.params` 是可信内部对象，不应需要 `except Exception`。

### M-02 transfers.py integrity 冗余字段

**文件**：`backend/iesplan/application/packages/transfers.py:959–960`

```python
"checks": {
    "zip_ok": True,
    "manifest_ok": True,
    "integrity_ok": True,
    "integrity_verified_objects": len(manifest.get("objects", [])),
},
```

在导入提案的 `review_summary` 中写入 `integrity_ok: True`，属于对内部校验结果的摘要记录，违反宪法 §2.6："不得重算、比对或存储 SHA-256、内容摘要、校验和或类似完整性字段"。这些字段在内部流程中无实际用途，只增加误导性。应删除 `integrity_ok` 和 `integrity_verified_objects`，只保留 `zip_ok` 和 `manifest_ok`（这两个是真实校验结果，不是摘要）。

### M-03 validation.baselineConfirm 丢弃后端 diagnostics

**文件**：`frontend/src/api/client.ts:1651`

```ts
.then((body) => ({ confirmed: asRecord(body).confirmed === true, diagnostics: [] }))
// 后端返回 diagnostics，前端硬编码为空数组
```

后端 `baseline-confirm` 端点返回 `{confirmed, diagnostics}`，前端抹掉了 diagnostics，调用方永远收到空诊断列表。如果后端在确认失败时返回阻断性诊断，前端无法呈现，用户不知道为何确认失败。

**修复**：将 `diagnostics: []` 改为从响应体解析：
```ts
diagnostics: asList<Diagnostic>(asRecord(body), 'diagnostics'),
```

### M-04 application/namespace.py 的宽泛 except 导致 rollback 噪声

**文件**：`backend/iesplan/application/namespace.py:37`

```python
except Exception:
    db.rollback()
```

`flush()` 的唯一预期异常是 `IntegrityError`（唯一约束冲突）。捕获 `Exception` 意味着任何其他错误（数据库连接中断、OperationalError）也会被 `rollback()` 后静默重试 20 次，掩盖真实问题。应精确捕获 `sqlalchemy.exc.IntegrityError`。

### M-05 前端 asList 兜底返回空数组掩盖格式错误

**文件**：`frontend/src/api/client.ts:433–439`

```ts
function asList<T>(body: unknown, key: string): T[] {
  if (Array.isArray(body)) return body as T[]
  const rec = asRecord(body)
  if (Array.isArray(rec.items)) return rec.items as T[]
  if (Array.isArray(rec[key])) return rec[key] as T[]
  return []   // 形状不符时静默返回空，不报告错误
}
```

当后端响应形状不符（如字段名改变、信封层级变化）时，`asList` 静默返回空数组，与宪法"禁止把失败解释为暂无数据"直接冲突。调用方若依赖此结果渲染列表，会显示"暂无数据"而非报错。

`projectVersions()` 已经做了显式形状检查（若无 `versions` 字段则抛错），但大多数其他接口没有。问题的影响面取决于后端是否在该项目期间改过信封，0.14 已有多次 error envelope 清理，风险不低。

## 三、低严重性问题

### L-01 client.ts 单文件过大，功能边界混合

**文件**：`frontend/src/api/client.ts`（2186 行）

单文件承担了：底层 fetch 封装、401 处理、适配辅助函数（20+个）、模块级缓存、类型定义、全部 API 方法实现（auth/projects/model/datasets/config/tasks/results/exports/admin）。这与宪法 §9 "features 垂直切分" 的目标相悖。虽然文件本身内聚，但当前结构使每个 feature 测试和维护都需要改这一个文件。

0.15 及以后的 Provider SDK 接入会进一步膨胀此文件。建议在 0.14 退出后（非阻断）按 feature 拆分。

### L-02 前端 `unwrapBody` 支持两种成功信封格式

**文件**：`frontend/src/api/client.ts:242–250`

```ts
function unwrapBody<T>(body: unknown): T {
  if (body && typeof body === 'object' && !Array.isArray(body)) {
    const record = body as Record<string, unknown>
    if (record.ok === true && 'data' in record) {
      return record.data as T
    }
  }
  return body as T
}
```

同时兼容裸 JSON 和 `{ok:true, data:...}` 两种信封。这是已知的兼容转换层（ADR-0005 命名键包装），但若后端已统一到命名键包装，此兼容逻辑应有计划移除，否则在出现意外响应时会静默透传错误形状。

### L-03 subprocess.Popen argv 未做白名单校验

**文件**：`backend/iesplan/computation/runtime/local_process.py:495`

```python
proc = subprocess.Popen(
    argv,
    cwd=run_cwd,
    env=environ,
    ...
    start_new_session=True,
)
```

`argv` 来自 `DeploymentPolicy` / Solver Bundle 的结构化命令，不使用 `shell=True`，注入风险较低。但 Bundle 来源（YAML 文件）的 `argv[0]`（可执行路径）若不做白名单校验，存在路径遍历或替换可执行文件的可能。建议在 `DeploymentPolicy` 配置层对可执行文件路径做白名单检查。

### L-04 前端 admin.storage() 缺失 used_bytes 后端字段映射

已在 H-02 中标注，此处补充：后端 `admin/storage` 返回的 `objects` 对象字段名需要与前端对齐，建议同时检查后端响应结构和前端字段名。

## 五、0.14 退出条件核查

按 Roadmap 0.14 退出标准"从登录到导出的关键流程无兼容猜测、假资源或错误空数据降级"：

- **H-01**（模块级缓存）：**阻断** —— resultBodyCache 可导致 hourly 结果读取旧数据，pkgTaskCache 可导致 Excel 导出拿错评估，直接违反退出标准。
- **H-02**（used_bytes bug）：**阻断** —— 管理员存储视图显示错误数据，属于"错误空数据降级"之列。
- **M-03**（baselineConfirm 丢弃诊断）：**建议修复** —— 用户确认失败时无法看到原因，功能性缺陷。
- **M-04**（namespace except 过宽）：**次要** —— 不影响正常路径。
- **M-05**（asList 空数组兜底）：**建议修复** —— 与退出标准"无空数据降级"正面冲突，但需判断实际触发路径。
- 其余：可安排在 0.15 前完成。

## Codex 复核补充（2026-10-16）

复核原报告基线 `1f57e19`，并结合主线 `4973c71` 的工作台归属验收。以下裁决修正上文结论；原文保留为审查历史，不作为实施清单。

- **H-02 / L-04 不成立**：`storage_stats.objects.total_bytes` 是存储对象大小之和，不是磁盘容量；Settings 页面将其显示为已使用量。后端无 `objects.used_bytes`。前端未使用的重复字段可清理，但不能据此认定管理员页面显示磁盘已满，更不能臆造后端字段。
- **M-03 不成立**：`confirm_baseline` 成功响应为 `confirmed/confirmed_by/confirmed_at`，没有 `diagnostics`；失败走标准错误响应。前端该方法无实际调用方，不能新增解析来消费不存在的字段。
- **L-03 不成立**：SolverRuntime 已检查部署 executable allowlist；LocalProcessProvider 解析已注册绑定、验证参数，以 `binding.path` 构造 argv。不再新增重复白名单或安全防御层。
- **H-01 部分成立，但错误结果推断未获证明**：业务缓存和隐式调用依赖确需清理；包 ID 到任务 ID 的映射不等于缓存评估，评估列表每次重新请求；completed 任务也不能重试。下载 Map 是临时下载句柄登记，不可仅因使用 Map 就认定为业务缓存或要求迁入 React context。按真实消费者和所有权处理，不增加 TTL。
- **M-01 / M-02 / M-04 有实际残留**：单位模块的真实业务异常为 `UnitError`；导入提案有冗余完整性宣称字段及对应断言（不代表存在 SHA 处理），保留真实的公开上传 ZIP/manifest 输入校验；命名空间分配捕获所有 flush 异常并全局 rollback，不能只把异常名改为 `IntegrityError` 就视为事务边界问题已解决，须区分真正的命名空间碰撞与其他失败并保护调用方事务。
- **M-05 / L-01 / L-02 的版本优先级需更正**：feature 边界、模块级业务缓存和响应形状猜测清理已在 0.14 Roadmap 内，不能直接推迟到 0.15。应按公开 DTO 与真实消费链收敛，不用另一套内部形状复核替代兼容猜测。

本报告及其补充均不证明 0.14 全部退出验收已完成；各切片须有独立代码审阅与相称证据。本文件保持本地忽略，不纳入 Git。
