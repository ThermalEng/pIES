# IES Plan 产品版本 2 Roadmap

- 制定日期：2026-08-20
- 依据：`IES-Plan-Design-Input.rpd`、`docs/rpd-implementation-gap-review.md`
- 适用范围：产品版本 2 / 二阶段
- 文档状态：路线图草案，用于范围、依赖和交付顺序管理

---

## 1. Roadmap 目标

产品版本 2 在不破坏版本 1 核心不变量的前提下，扩展以下能力：

1. 扩充设备和能源系统建模范围；
2. 引入受控的外部 API 引用能力；
3. 提供问答式信息收集，降低建模和参数配置门槛；
4. 提供 AI 辅助报告生成；
5. 提供 AI 辅助 Excel 标准化；
6. 支持本地 Open WebUI 等本地 AI 服务对接；
7. 继续保持项目版本、数据版本、计算快照和结果证据的可追踪性；
8. 不把版本 2 扩展成生产实时调度、设备控制或浏览器内正式求解系统。

### 1.1 二期范围

根据 RPD，二期原始范围包括：

- 风电；
- 燃气内燃机；
- 余热锅炉；
- 吸收式制冷机；
- 热储能；
- 冷储能；
- 问答式信息收集；
- AI 报告生成；
- AI Excel 标准化；
- 本地 Open WebUI 对接。

本路线图新增：

- **外部 API 引用功能**：在用户授权和项目溯源约束下，调用受控外部数据/服务 API，并将响应以可复现、可审计的方式引用到项目数据、参数辅助、问答、报告或标准化流程中。

### 1.2 明确不属于二期默认范围

以下内容不因二期扩展自动纳入：

- 实时生产运行计划；
- 实时调度；
- 设备控制或控制指令下发；
- 浏览器内正式求解；
- 外部身份提供方和外部角色自动映射；
- 未经注册、测试和权限隔离的任意第三方插件；
- 把外部 API 返回结果直接作为不可追踪的权威输入；
- 让 AI 直接修改项目权威数据或直接提交计算任务而不经过确认。

---

## 2. 现状与路线图原则

### 2.1 版本 1 审查中发现的前置问题

二期不应直接建立在当前所有问题之上。以下版本 1 问题必须在相应二期能力上线前修复或明确降级：

- 不确定性参数从前端到 Worker 的链路断裂；
- 失败样本可能被计为有效样本；
- 规划层目前是容量枚举/抽样加逐候选评价，不是完整规划级 MILP/MINLP；
- 多目标和 Pareto 计算尚未形成真实闭环；
- 工程参数、设备寿命、网络约束和财务结果部分未闭环；
- 结果页和 Excel 存在使用当前版本而不是计算快照版本的追踪风险；
- 永久版本的前端创建/恢复入口不完整；
- I/O Worker 仍有占位执行器；
- 数据库迁移、部署迁移和恢复验证入口不足；
- 用户数量、同时在线人数、CSRF、资源限制和最低分辨率提示尚未完成系统验收。

### 2.2 二期核心原则

1. **先基础设施，后 AI 和外部服务。**
2. **先建立数据和证据契约，后接入供应商。**
3. **设备扩展与计算引擎扩展分开交付。**
4. **外部 API 只能提供可审计的引用或候选输入，不能绕过快照和版本体系。**
5. **AI 产出默认是建议、草稿或待审核结果，不直接改变权威项目状态。**
6. **每个新设备必须有数据、单位、方程、约束、财务和验证案例。**
7. **每个外部服务必须可禁用、可超时、可降级，并支持离线继续使用已有数据。**
8. **每个阶段都必须有可独立验收的垂直切片，不以“所有二期功能完成”作为唯一交付节点。**

---

## 3. 总体顺序

建议按以下顺序推进：

```text
P0：版本1收口与二期基础契约
        ↓
P1：外部API引用基础设施
        ↓
P2：新增设备模型与计算引擎扩展
        ↓
P3：问答式信息收集
        ↓
P4：AI Excel标准化
        ↓
P5：AI报告生成
        ↓
P6：本地Open WebUI对接与统一AI编排
        ↓
P7：二期整体验收、迁移和发布
```

其中：

- 外部 API 不是最后附加的接口，而是问答、数据标准化和报告生成可能共用的基础能力；
- 新增设备模型应先于依赖这些设备的问答、报告和 Excel 生成；
- AI Excel 标准化应先于 AI 报告生成，因为报告需要依赖标准化后的数据和质量结论；
- 本地 Open WebUI 对接放在 AI 能力稳定后，避免同时调试模型服务、业务提示词和基础数据契约。

# 4. 阶段 P0：版本 1 收口与二期基础契约

## 4.1 目标

在二期开发前，先把版本 1 的结果正确性、版本追踪和部署边界收口，建立二期不得破坏的基础契约。

## 4.2 必须完成的工作

### 计算正确性

- 修复不确定性任务参数结构不一致；
- 统一 `distribution` / `distributions` 字段；
- 明确任务种子与计算快照种子的优先级；
- 修复失败样本状态、有效样本数和统计分母；
- 对样本级取消、重试、恢复和部分完成建立可测试语义。

### 结果与版本追踪

- 结果页使用计算快照绑定的项目版本和数据版本；
- Excel 使用 `snapshot.project_version_id`，禁止读取项目当前版本代替历史输入；
- 项目包、Excel、结果页统一使用同一份快照元数据；
- 补齐永久版本创建、查看和恢复的前端入口。

### 求解和结果状态

- 明确规划层枚举/抽样的降级语义；
- 补充可行性、停止原因、Gap、未证明最优、数值失败等状态；
- 明确单目标与多目标当前版本边界；
- 为新增设备和外部数据建立统一模型/数据注册契约。

### 运维和安全

- 完成数据库迁移和部署迁移入口；
- 验证对象存储、数据库和项目包恢复流程；
- 明确 Redis 不可用时的登录限速策略；
- 补齐 CSRF、用户数/在线数门禁和最低分辨率提示；
- 建立 Docker 级并发、资源限制、超时和孤儿进程验收。

## 4.3 退出标准

- 版本 1 关键验收不再存在已知的结果快照错配；
- 不确定性测试能够证明参数生效、无效样本隔离、统计分母正确；
- 版本、数据、快照、证据包和导出之间可互相追踪；
- 迁移、备份、恢复和 Docker 部署有可重复操作入口；
- 二期扩展契约已经冻结并有自动化校验。

# 5. 阶段 P1：外部 API 引用基础设施

## 5.1 目标

建立安全、可控、可追踪的外部 API 引用层，为外部数据、问答、Excel 标准化、AI 报告和本地 AI 服务提供统一基础能力。

这里的“外部 API 引用”不是简单增加一个 HTTP 客户端，而是建立完整的：

```text
API 提供方注册
    ↓
请求策略与权限
    ↓
请求/响应缓存
    ↓
数据质量与转换
    ↓
项目/数据版本绑定
    ↓
可审计引用
```

## 5.2 首批建议支持的引用类型

首批只支持有明确价值、可验证和可降级的类型：

1. **外部气象或环境数据 API**
   - 太阳辐照、环境温度、风速等；
   - 用于数据补充、对比或预填，不默认覆盖用户上传的权威数据。

2. **外部能源价格或排放因子 API**
   - 电价、燃气价格、排放因子等；
   - 必须记录地区、时间范围、币种、单位和有效期。

3. **项目辅助资料 API**
   - 仅用于信息查询和引用；
   - 不直接写入项目权威模型。

4. **AI 服务 API**
   - 单独作为 AI Provider 类型管理；
   - 与普通业务数据 API 使用不同的权限、日志和数据脱敏策略。

## 5.3 核心功能

### Provider 注册与受控扩展

- 外部 API Provider 使用白名单注册；
- 每个 Provider 声明：
  - 唯一标识；
  - 版本；
  - endpoint；
  - 能力；
  - 请求参数；
  - 响应 schema；
  - 单位；
  - 时间和地区语义；
  - 认证方式；
  - 限流和超时策略；
  - 兼容性和迁移规则；
- 禁止任意用户提交 URL 后直接访问服务器网络；
- 禁止 Provider 访问用户会话、任意数据库连接和任意服务器路径。

### 凭证与权限

- API Key、OAuth Token 等凭证使用密钥存储，不进入普通项目导出；
- 管理员可启用/禁用 Provider；
- 项目所有者明确授权后才能将外部结果绑定到项目；
- 查看者只读使用已绑定引用，不能替所有者新增外部连接；
- 外部请求日志不能泄露密钥和完整敏感请求体；
- 允许仅使用公开、无需凭证的 Provider。

### 请求与缓存

- 请求超时、重试、退避、限流和熔断；
- 对相同 Provider、参数、时间范围、版本建立内容哈希；
- 缓存响应并记录获取时间；
- 区分“实时响应”“缓存响应”“过期缓存”“离线不可用”；
- 支持管理员清理不再被项目引用的缓存对象；
- 支持离线环境继续使用已缓存且未被标记失效的结果。

### 数据转换与质量

- 外部响应先进入临时对象或外部引用版本，不直接覆盖用户数据集；
- 执行单位、时区、UTC 偏移、时间分辨率、缺失值和范围校验；
- 转换结果生成新的数据集版本；
- 保留原始响应、转换规则、质量报告和错误定位；
- 用户确认后才能绑定到计算快照。

### 证据和溯源

每次外部 API 引用至少记录：

- Provider 标识和版本；
- endpoint 标识；
- 请求参数的脱敏摘要；
- 请求时间和响应时间；
- 数据覆盖范围；
- 地区和时区；
- 原始响应或内容哈希；
- 转换规则版本；
- 质量检查结果；
- 缓存状态；
- 许可和使用限制；
- 发起用户、项目和任务；
- 是否被实际计算使用。

## 5.4 建议交付顺序

1. Provider 注册契约和白名单；
2. 凭证管理与权限模型；
3. 请求代理、限流、超时和缓存；
4. 外部引用对象和数据版本模型；
5. 数据转换、校验和人工确认；
6. 项目快照、结果和导出的溯源；
7. 首个气象/环境 Provider；
8. 首个价格或排放因子 Provider；
9. 离线降级和失败演练。

## 5.5 退出标准

- 未注册 URL 无法被调用；
- API 凭证不出现在日志、项目包和普通 Excel 中；
- 外部响应可以重现、缓存、撤销和审计；
- 外部数据能够形成新的数据集版本，并经质量校验后参与计算；
- 网络断开时已有缓存和用户上传数据仍可使用；
- 外部 API 失败不会破坏项目草稿、历史版本和既有结果。

# 6. 阶段 P2：二期设备和能源系统模型扩展

## 6.1 目标

在统一设备注册、数据契约和验证体系上，增加 RPD 二期设备，而不是仅增加前端卡片或参数字段。

## 6.2 建议设备交付顺序

建议按能量耦合复杂度和依赖关系排序：

### P2-A：热储能和冷储能

优先原因：

- 与电池储能具有相似的 SOC/容量/充放约束结构；
- 可以先验证储能通用接口；
- 可复用周期边界、损耗、功率上限和容量约束框架。

必须覆盖：

- 热/冷能量状态；
- 充放热/冷功率；
- 充放效率；
- 自放热/冷损失；
- 温度或可用容量边界；
- 初始和终止状态；
- 设备寿命和更换；
- 与热泵、锅炉、电制冷机和负荷的连接规则。

### P2-B：风电

依赖：

- 外部气象 API 或用户风资源数据；
- 统一时序数据校验；
- 风速到功率曲线转换；
- 并网和弃风约束。

必须覆盖：

- 风速高度和测量条件；
- 功率曲线版本；
- 切入、额定和切出风速；
- 机组可用率；
- 额定容量和并网容量；
- 弃风、限发和反送限制；
- 设备投资、运维和寿命。

### P2-C：燃气内燃机

依赖：

- 燃气价格和排放因子数据；
- 电热联供能流接口；
- 启停和最小出力逻辑。

必须覆盖：

- 电效率；
- 余热回收效率；
- 最小/最大出力；
- 启停状态；
- 最小开停机时间；
- 燃气消耗；
- 排放；
- 维护和启停成本；
- 与余热锅炉、热负荷和电负荷的耦合。

### P2-D：余热锅炉

依赖：

- 燃气内燃机或其他余热源的热流接口；
- 热网和热负荷模型。

必须覆盖：

- 余热输入；
- 热回收上限；
- 热效率；
- 最低稳定出力；
- 热水/蒸汽等介质定义；
- 热损失；
- 与燃气锅炉和热泵的互斥/协同约束。

### P2-E：吸收式制冷机

依赖：

- 余热锅炉或热源设备；
- 冷网传输和冷负荷模型；
- COP 与热源温度语义。

必须覆盖：

- 热驱动制冷；
- COP 或性能曲线；
- 最小稳定出力；
- 热源不足时的可用性；
- 冷量上限；
- 冷却水/泵耗电；
- 与电制冷机的协同和切换。

## 6.3 统一计算要求

每个新设备必须同步实现：

- Registry 声明；
- 参数和单位；
- 端口和连接校验；
- 时序运行模型；
- 规划变量和约束；
- 财务 CAPEX/OPEX；
- 排放和工程指标；
- 不确定性分析支持；
- 导入导出 schema；
- 诊断和错误文案；
- 合成案例；
- 代表性工程案例；
- 参考结果和容差。

## 6.4 退出标准

- 每种设备都有至少一个可手算或可枚举的确定性案例；
- 每种设备至少有一个与其他设备耦合的案例；
- 三种数据分辨率都能保持同一单位和结果语义；
- 新设备能进入项目版本、计算快照、结果、Excel 和项目包；
- 不确定性分析能正确扰动新设备相关输入；
- 设备新增不会破坏版本 1 项目的读取和重新计算。

# 7. 阶段 P3：问答式信息收集

## 7.1 目标

将复杂的建模、数据和参数配置转化为有上下文的问答流程，但最终仍生成可审计的项目草稿和待确认命令。

## 7.2 功能范围

- 根据项目类型、能源需求和现有设备生成问题清单；
- 分阶段收集：
  - 项目基本信息；
  - 地理位置和气象需求；
  - 电/热/冷负荷；
  - 存量设备；
  - 新建设备；
  - 经济和财务假设；
  - 可靠性和规划偏好；
- 对缺失信息给出“必填、建议、可跳过”分类；
- 将答案映射为草稿变更预览；
- 显示单位、范围、来源和不确定性；
- 支持用户逐项确认、修改和撤销；
- 支持从已有项目模型反向生成问答上下文；
- 提供中英文一致的术语和错误提示。

## 7.3 与 AI 的边界

- 问答引擎可以提出问题和建议默认值；
- AI 不直接写入项目权威版本；
- 所有变更必须经过用户确认；
- 外部 API 返回的信息必须显示来源和获取时间；
- 不确定信息不能伪装为用户已确认的工程参数；
- 问答过程需要保留版本、回答、来源和最终采纳状态。

## 7.4 依赖

- P0 的草稿命令和永久版本闭环；
- P1 的外部 API 引用和数据质量报告；
- P2 的设备 Registry 和参数 schema；
- 统一单位、错误文案和帮助元数据。

## 7.5 退出标准

- 用户可从空项目完成一条端到端问答流程；
- 每个回答都能追溯到生成的草稿变更；
- 用户拒绝或修改建议后，不会留下隐式写入；
- 外部数据来源、AI 建议和用户确认状态可区分；
- 断网时仍可完成不依赖外部服务的问答流程。

# 8. 阶段 P4：AI Excel 标准化

## 8.1 目标

将格式不统一、字段名不一致或存在轻微结构差异的用户 Excel 转换为系统可校验的数据集草稿，并保留原始文件和转换证据。

## 8.2 功能范围

- 识别工作表、表头、合并单元格和数据区域；
- 识别中英文列名和常见同义词；
- 识别时间列、负荷列、电价列、温度列、辐照列等；
- 识别单位并提出单位转换建议；
- 识别时间分辨率和固定 UTC 偏移；
- 检查缺失值、重复值、乱序、异常范围和列类型；
- 生成标准化预览和差异报告；
- 支持用户逐列确认；
- 确认后生成新的数据集版本；
- 原始 Excel、标准化结果、映射规则和质量报告均可导出。

## 8.3 安全和质量要求

- 原始文件只读保存；
- 公式、宏、外部链接和嵌入对象默认不执行；
- 不能通过 Excel 内容触发任意代码或任意网络请求；
- AI 识别结果必须有置信度和待确认状态；
- 标准化失败必须定位到工作表、行、列和单元格；
- 标准化结果不能绕过数据集校验门禁；
- 不能把 AI 推断的值标记为原始事实。

## 8.4 依赖

- P1 外部 API/数据引用 schema；
- P2 设备和数据字段注册；
- 版本 1 已完成的数据集校验、对象存储和项目包机制；
- 问答式信息收集可复用字段确认组件。

## 8.5 退出标准

- 至少覆盖三种常见 Excel 模板差异；
- 标准化结果必须经过同一套数据质量校验；
- 用户可以逐项接受、拒绝和修改 AI 映射；
- 生成的数据集版本可用于计算并能回溯原始文件；
- 离线部署下仍可使用规则型标准化，AI 能力不可用时有明确降级提示。

---

# 9. 阶段 P5：AI 报告生成

## 9.1 目标

基于已完成且可追踪的计算结果、工程指标、财务指标和质量状态生成双语报告草稿，减少人工整理，但不改变权威结果。

## 9.2 报告内容

- 项目和计算快照摘要；
- 输入数据和外部 API 引用清单；
- 模型、设备和主要假设；
- 规划目标、约束和算法；
- 求解状态、Gap、停止原因和适用范围；
- 财务指标；
- 运行、排放和工程指标；
- 可靠性分析统计和无效样本说明；
- Pareto 候选和用户选择；
- 风险、缺失数据和待确认事项；
- 结果局限性和不应作出的运行控制解释。

## 9.3 生成规则

- 以结果证据包和计算快照为唯一事实来源；
- AI 只能重述、归纳和解释已存在的结构化结果；
- 所有数字必须引用来源字段；
- 缺失或不确定值必须明确标注；
- 不允许 AI 自行补造数据、结论或经济假设；
- 报告为草稿，用户确认后才能导出正式版本；
- 报告记录使用的模型、提示模板、AI Provider 和版本；
- 支持重新生成，并保留不同报告版本。

## 9.4 依赖

- P0 的快照和结果追踪修复；
- P1 的外部引用清单；
- P2 的设备和工程指标；
- 可靠性和多目标结果状态完整；
- P4 的数据质量和标准化结果。

## 9.5 退出标准

- 报告中的每个关键数字都能定位到结果证据；
- 失败、不可行、低质量和未证明最优结果不会被描述为成功方案；
- 中英文报告结构和关键术语一致；
- AI 服务不可用时仍可导出结构化非 AI 摘要；
- 报告生成不会修改项目版本、计算快照和原始证据。

---

# 10. 阶段 P6：本地 Open WebUI 对接与统一 AI 编排

## 10.1 目标

支持用户在本地部署的 Open WebUI 或兼容 OpenAI API 的本地模型服务上运行问答、标准化辅助和报告生成，降低数据离开本地部署环境的风险。

## 10.2 对接范围

- 可配置本地 AI endpoint；
- 支持 OpenAI-compatible chat/completions 等最小能力；
- 管理员启用/禁用本地 AI Provider；
- 连接测试和模型能力发现；
- 请求超时、重试、限流和取消；
- Provider 不可用时回退规则引擎或结构化摘要；
- 支持按功能选择不同模型；
- 明确上下文长度、文件上传和工具调用能力。

## 10.3 数据边界

- 默认只发送用户明确选择的项目数据；
- 支持脱敏、字段白名单和上下文预览；
- 禁止默认发送密码、API Key、会话凭证和未授权项目；
- 本地 Provider 与外部云 Provider 使用不同的信任级别；
- 请求和响应保存内容哈希及元数据，敏感正文按配置保留；
- AI 不直接执行数据库写入、文件系统访问或外部网络请求。

## 10.4 依赖

- P1 Provider 注册和凭证/权限体系；
- P3 问答协议；
- P4 标准化输入输出；
- P5 报告生成模板和证据引用；
- 部署环境网络边界和离线降级机制。

## 10.5 退出标准

- 本地 Open WebUI 可独立完成问答和报告草稿生成；
- 用户能看到发送给模型的上下文摘要；
- 本地 AI 不可用时核心版本 1 功能不受影响；
- 本地和外部 Provider 的权限、审计和数据边界可区分；
- AI 产出仍必须经过用户确认，不改变权威项目状态。

# 11. 阶段 P7：二期整体验收与发布

## 11.1 端到端场景

至少覆盖以下完整场景：

1. 用户通过问答创建包含风电和电池的项目；
2. 从外部气象 API 获取数据，生成外部引用版本；
3. 用户上传并通过 AI 标准化负荷 Excel；
4. 使用燃气内燃机、余热锅炉、吸收式制冷机和冷储能构建冷热电系统；
5. 运行规划、可靠性分析和多目标结果查看；
6. 生成带来源、快照和质量状态的双语 AI 报告；
7. 将项目包和 Excel 导出后在离线部署中恢复；
8. 通过本地 Open WebUI 重新生成报告草稿；
9. 禁用外部 API 和 AI 服务，确认既有缓存和核心计算仍可用；
10. 变更项目和数据版本后，确认历史结果仍保持原始追踪关系。

## 11.2 必须验证的不变量

- 项目版本和计算快照不可变；
- 外部 API 引用不能绕过数据版本和质量门禁；
- AI 产出不能直接成为权威项目状态；
- 外部数据、AI 建议、用户确认和计算输入可区分；
- 历史结果不会被当前项目版本或最新数据版本污染；
- 项目包导入创建新项目身份，原授权关系不迁移；
- 外部 API 失败不破坏离线能力；
- 新设备未通过验证时不能进入生产 Registry；
- 失败、不可行、低质量和未证明最优状态不会被报告为成功；
- 凭证、敏感信息和未授权项目不会泄露给外部服务。

## 11.3 发布门禁

### 功能门禁

- 所有二期设备完成模型、校验、计算、结果和导出闭环；
- 问答、Excel 标准化、报告生成和 Open WebUI 均有可撤销、可确认和可审计语义；
- 外部 API 引用具备 Provider 白名单、缓存、降级和溯源。

### 正确性门禁

- 每种新增设备有合成案例和代表性工程案例；
- 每个关键指标有参考结果和容差；
- 多分辨率和不确定性分析结果语义一致；
- 历史结果快照追踪测试通过；
- AI 报告关键数字与证据包自动交叉校验通过。

### 安全门禁

- 凭证不出现在日志、项目包和普通导出；
- 外部请求只能访问白名单 Provider；
- AI 上下文经过权限和脱敏过滤；
- 用户确认前不会写入权威版本；
- 外部服务故障和超时不会造成任务无限等待。

### 运维门禁

- Docker 部署、迁移、升级、回滚和恢复均有固定操作入口；
- 计算队列与 I/O 队列具有资源隔离；
- 外部 API 和 AI Provider 的健康状态可观测；
- 缓存、原始响应、转换对象和报告版本可清理但不误删被引用对象；
- 版本 1 项目可以在版本 2 中读取、查看和重新计算。

# 13. 风险与控制措施

| 风险 | 影响 | 控制措施 |
| --- | --- | --- |
| 新设备只完成 UI，未完成能流和规划约束 | 结果不可用 | 每种设备必须以垂直切片交付，并包含合成案例、求解、财务和导出 |
| 外部 API 供应商响应不稳定 | 计算不可复现 | Provider 版本、响应缓存、内容 hash、转换版本和离线降级 |
| 外部数据覆盖用户权威数据 | 历史结果被污染 | 外部响应先生成独立引用版本，用户确认后才能绑定快照 |
| AI 生成错误参数或结论 | 工程和财务误判 | 结构化 schema、置信度、用户确认、结果证据交叉校验 |
| 外部 API Key 泄露 | 安全和合规风险 | 密钥存储、脱敏日志、权限隔离、导出排除和轮换 |
| 本地 Open WebUI 接口不兼容 | AI 功能不可用 | Provider 能力发现、最小兼容协议、规则引擎和非 AI 降级 |
| 二期设备扩大求解规模 | 任务超时和资源耗尽 | 规划规模基准、设备组合白名单、任务资源额度和超时状态 |
| 版本 1 结果与二期模型不兼容 | 历史证据不可读 | schema 版本、迁移规则、旧项目只读兼容和重新计算提示 |
| AI 报告掩盖失败状态 | 错误决策 | 报告模板强制展示业务结局、适用范围、失败原因和未证明最优状态 |

# 14. 最终建议

二期最合理的交付路径不是“先做 AI，再补模型”，而是：

1. 先修复版本 1 的快照、结果、任务和部署基础问题；
2. 建立外部 API 的 Provider、权限、缓存、质量和溯源基础设施；
3. 逐类实现新增设备，并为每类设备建立可验证的计算闭环；
4. 在结构化模型和数据契约稳定后，再交付问答式信息收集；
5. 在标准化数据稳定后交付 AI Excel 标准化；
6. 在结果证据和质量状态稳定后交付 AI 报告生成；
7. 最后接入本地 Open WebUI，作为统一 AI Provider 的部署选项；
8. 通过端到端、离线、迁移、权限和恢复验收后再发布二期。

其中，**外部 API 引用功能应作为二期早期基础能力，而不是放到 AI 功能之后临时接入**。它同时影响气象/价格数据、问答建议、Excel 标准化和报告引用，越晚建设，后续越容易出现数据来源不一致、缓存不可复现、权限边界不清和历史结果无法追踪的问题。
